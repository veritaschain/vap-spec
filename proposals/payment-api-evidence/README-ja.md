# 決済APIの認可証拠 — 参考提案

**状態：提案・未採択。参考設計。** 2026年11月6日JSTに、リポジトリの基準コミット
`1e6fff1bab50caf467b2a6b9e9f7de3d23d1c67a` と照合。[English](README.md)

将来の決済アダプターで検討する証拠の対応付けを示します。規範フィールド、プロファイル登録、
適合主張は追加しません。別途追加した[オフラインの合成証拠実験](../../experiments/payment-api-evidence/README-ja.md)
では、8つの候補群に対応する証拠上の区別を検証します。別の[管理された実行時パイロット](../../experiments/payment-runtime-pilot/README-ja.md)
では、専用のループバック模擬決済APIに対し、永続的な送出管理と照合を検証します。PAY-06の実行時検証の一部と、
PAY-08のローカル記録・世代の部分を対象にし、基本パイロットには業務認可と独立収集を含めません。
追加の[承認パイロット](../../experiments/payment-authorization-pilot/README-ja.md)では、使用済みにする時点で合成した
起票者・承認者の条件を検証し、元の承認判定記録を送出記録と一括保存します。PAY-02/PAY-03の一部と、
PAY-04の提示された状態情報を対象にし、本番の本人承認や権威元の最新状態の強制は実証しません。
追加の[収集パイロット](../../experiments/payment-collector-pilot/README-ja.md)は、別のループバックプロセスに
元の承認記録と提供者受領証を保全し、最初の管理されたPOSTの前に収集条件を検証します。
証拠回収では送金を再送しません。別ストア・別鍵も同じ運用者とOSユーザーの管理下です。
**アダプターの受入条件全体は未実証**です。実銀行の決済や独立運営の証拠保管サービスは試験していません。

## 出典と範囲

CERT-Inの[11月4日の更新][c58]はCRAFTY FALCONと4つのAI攻撃基盤を挙げ、決済APIの悪用と
暗号資産ウォレットの窃取被害を報告しています。[10月9日の勧告][c46]には長期トークンの窃取と、
取引段階の結合・二次承認の推奨が既にあり、[10月15日の勧告][c49]も不完全な対策後の再攻撃を
記載しています。[Reuters][reuters]が併記した約200万ドルの別事案と本キャンペーンの関連は
確定していません。これらは出典に帰属する公開報告であり、VSOが取得したフォレンジック証拠ではありません。

関連する[サイトの出典確認PR #202][site-review]で、日付・主張・出典を区別しています。
同PRは2026年11月6日にマージされ、[CRAFTY FALCONの項目][site-entry]を公開済みです。
出典確認の公開は、本提案の採択や実装の有効性の検証を意味しません。

[現行レジストリ](../../spec/v1.2/README.md)では、**VAP v1.2 Draft 3**、**VCP v1.2の仕様GA**、
**DAP v0.1.0 Working Draft**を区別しています。VCPの金融・アルゴリズム取引という対象範囲だけで、
汎用決済やウォレット保管のプロファイルが確立するわけではありません。本提案はそれらの状態を変更せず、
CERT-Inによる推奨も主張しません。

## 証拠に対応付ける項目の案

**1. 正確な操作と実行条件。** テナント、環境、ワークロード・実行単位、観測した主体、宣言された
委譲範囲、対象APIを識別します。送金元口座、送金先・受取人、操作、正確な金額と通貨、要求・実際に
送るデータのダイジェスト、操作ID、nonce・冪等性の適用範囲、ポリシー版・ダイジェスト、有効期間を
結び付けます。金額の単位と正確な表現が必要です。版を持つアダプターで正規化方法とAPIバイト列から
業務上の意味への対応を定義します。ダイジェストだけでは銀行のデータを解釈できず、送金先の妥当性も証明できません。

**2. 業務上の承認。** 起票者・承認者のそれぞれの承認を、同じ操作とポリシーに結び付けます。
別途信頼した本人・役割の情報源から、権限と職務分離を確かめます。署名や鍵が2つあっても、独立した
2人とは限りません。検証の信頼基点を証拠一式の自己申告だけで決めることはできません。
承認の発行・期限には、時刻源の前提と送出に対する順序を明示します。

**3. 実行直前の状態と復旧。** 認証情報・委譲権限の最終状態の観測を、操作、承認、発行主体、設定、
復旧・失効の世代に結び付けます。観測時刻と鮮度を判断する根拠も記録します。実行前の失効が観測されれば
認可に反し、観測がない・古い場合は不明です。新しい状態記録だけでは、確認から実行までの時間差を
解消できません。実行との不可分な連携、保護されたポリシー状態、永続的な使用済み要求の台帳は別途必要です。
鍵の更新や一度の再試験の成功だけで、すべての侵入維持経路を根絶したとはいえません。

**4. 観測した制御経路。** 本番、テスト、クラウド管理、デプロイ、署名のどの経路を調べたか、設定の
識別情報、観測者、時刻を記録します。記録の署名が正しくても、迂回経路が観測されることはあります。
未観測の経路は不明です。実行と証拠の権限をともに掌握した悪意ある管理者は、想定する分離を破れます。
名前の異なる鍵を使うだけでは、このリスクは解消しません。

**5. 実行と結果。** 送出意図、API呼出し、真正性を検証した提供者の受領・結果証明、照合証拠を、
個別操作に結び付けます。受理、処理中、決済完了、失敗、取消し、不明を区別します。
HTTPでの成功は決済完了の証明ではありません。銀行・決済事業者の結果証明は、その信頼した提供者の
表明であり、VSOの独立観測ではありません。不明な結果は読み取り専用で照合し、応答がないことを
未実行とみなしたり、未解決の送金を自動で再送したりしません。

**6. 証拠保管とプライバシー。** 独立した収集者を設ける場合は、実際に保全した証拠を特定して受領を
確認し、収集範囲、欠落、チェックポイント、復旧世代を示します。これはVSOの設計案であり、
CIAD-2026-0058が指定する保管構成ではありません。署名対象の原バイト列と、別途採用した信頼鍵の
由来を保ちます。収集後の完全性検査では、収集前の欠落や虚偽を回復できません。秘密鍵、ベアラートークン、
不要な口座・個人データを含めません。可能な範囲で秘匿した参照、アクセス制御、保存期限を用います。
仮名やダイジェスト、特に推測しやすい値のダイジェストも、機微な情報を漏らす可能性があります。

## アダプターの受入条件案 — 実験による部分的な検証

**記録の完全性（I）、個別操作の認可（A）、実行内容の一致（E）、観測された制御状態（C）**を分けます。
これは議論用の区分であり、VAPの判定値や新しいデータ形式ではありません。裏付けのある観測も、信頼した
情報源と記録した範囲に限定されます。証拠不足を理由に実行受付を拒否しても、事後の評価は「不明」のままです。

| 候補 | 合成環境で試す条件 | 確かめる区別 |
| --- | --- | --- |
| PAY-01 | 対応する承認、範囲付きの観測、真正性を検証した決済証拠がそろう | Iを検証でき、A・Eに裏付けがあっても、Cは観測した経路と時点に限る。全体の安全判定にしない。 |
| PAY-02 | 別人を要求するポリシーに対し、有効な2つの署名鍵が同一人物に対応する | Iが検証できてもAは違反。本人への対応自体が不明ならAも不明。 |
| PAY-03 | 新たに署名された実行の送金先・金額・通貨・テナント・環境が承認と異なる | Iが検証できても承認との結合とEは不成立。変更しない正常例も併せる。 |
| PAY-04 | 実行前に失効している。別の変種として、最終状態の観測が欠落・古い | 失効の証拠があればAは違反、観測不足なら不明。いずれも証拠に基づく実行受付を認めない。 |
| PAY-05 | クラウド・デプロイ経路がゲートを迂回する。別の変種として必須経路が未観測 | Iが検証できても、観測した迂回はCの違反、観測不足はCが不明。 |
| PAY-06 | 応答喪失後に操作IDを再利用する、または内容を変えて再利用する | 未解決のEは不明のまま。自動で書き込みを再送しない。実アダプターの永続的な使用管理を検証するまで重複抑止を主張しない。 |
| PAY-07 | 決済証拠のないHTTP 200。別の変種として、真正な結果証明が別の操作を示す | 前者のEは不明、後者は不一致。結果証明が真正でも、内容の不一致は解消しない。 |
| PAY-08 | チェックポイント前に収集が停止し、認証情報更新後に旧世代の復旧記録を提示する | 既知の欠落を記録し、確認できた世代・結合の不一致を拒否。未観測の操作や根絶完了は不明のまま。 |

## レビューへの引き継ぎ

完全な実装には、認可・収集・提供者の意味の統合、正常性を確かめた成功対照、アダプターの実際の失敗を示す
負の対照が必要です。オフラインの実験は署名付き合成証拠を検証し、エンドポイントを実行しません。
追加した実行時パイロットでは、実際のローカル使用管理とプロセス復旧、模擬残高の変化、自動再送しない動作を
検証します。ただし、PAY-06とPAY-08のすべての一連の保証は立証しません。追加の承認ラッパーは、別の模擬事前条件を
この実行系につなぎ、事後検証器を実行前の認可として使いません。署名付き状態情報は許容した鮮度内でも現実の最新状態とは
限らず、使用済み記録の確定後の失効と提供者の実行を不可分にする保証もありません。
収集の実験では、ローカルな停止、受領応答の喪失、証拠回収を実際に検証します。
送金結果と保全の観測を分け、事後の収集を当初の送出前条件へ格上げしません。
収集全体の完全性、外部アンカー、独立した保管は実証しません。
本物の送金認証情報や資金を使わず、信頼した本人情報、失効状態、銀行側・収集者側の
観測を用意します。入力された期待ラベル同士の一致ではなく、実質的な検証条件を調べます。

銀行固有のデータの意味、時刻源の信頼、実行との不可分な連携、再利用防止の保存状態、特権による迂回、
プライバシー、独立再現は未解決で、別途実装・レビューが必要です。本書は試験合格、本番運用の準備完了、
宣言した収集範囲外の完全性、正式採択を立証しません。

防御側が記録できるのは観測した要求や作用であり、攻撃者の非公開の内部判断を直接観測することはできません。
VAP/VCPの証拠だけでは、侵害や不正送金を防止せず、承認を強制せず、秘密情報を更新せず、
攻撃が一度も起きなかったことも証明しません。
