# ウォレット操作の認可証跡 — 参考提案

**位置付け：未採択の参考提案・実験。** VAP v1.2 の規範要件、DAP の採択状態、既存の固定証跡は変更しません。新たな汎用プロファイルの提案でもありません。[English](README.md)

## 何を検証するか

開発者環境や社内 AI ツールの侵害が、デプロイ権限やウォレット署名基盤まで到達する場合、正しい認証情報や暗号署名が存在するだけでは、個別操作の認可を確認できません。また、アプリケーションの停止と、オンチェーンに残る委譲コードの解除は別の事象です。

[Binance の事故報告](https://www.binance.bh/en/blog/community/3229153443759566763)と[WIRED の報道](https://www.wired.com/story/binance-says-hackers-used-well-known-tricks-to-carry-out-a-dollar634-billion-heist/)を動機とする、範囲を限定した実験です。実際の事故の認証情報・署名・フォレンジック資料は含みません。侵入の再現、被害額・攻撃主体の確定、AI の自律攻撃の立証は行いません。テストの資格情報、承認、ワークロード、証跡はすべて合成データです。

## 既存実装との関係

既存の pre-record gate は認可、操作に一致する承認、失効確認、永続化した送信意図、結果不明時の自動再送防止を既に扱っています。OS-isolated gate と control-state evidence は、特権コントローラーと実行に接続されない統制確認の限界を既に示しています。

今回の追加は [wallet-authorization-evidence 実験](../../experiments/wallet-authorization-evidence/README.md)です。既存実装を置き換えず、ウォレット固有の項目、最終確認の署名、実行結果との対応、オンチェーン委譲状態の観測を追加します。DAP / VAP-AGENT の登録済み方向性に沿う参考事例であり、DAP の規範要件として採択したものではありません。

PR #43 の事故レビュー、PR #44 の一般的な証跡境界テストとは独立しています。PR #44 の未マージコードを取り込まず、同 PR の五つの主張を持つ v0 スキーマも変更しません。整合性と認可、観測欠落と否定を分離する考え方を、ウォレットの四つの主張へ適用します。

## 判定と受入条件

| 判定 | 確認対象 |
| --- | --- |
| `integrity` | 呼出側が役割別に信頼した鍵で、提示された Ed25519 署名を実検証する。証跡の完全性や認可は推定しない。 |
| `authorization` | 正確な操作を、署名済みポリシー・承認・最終失効スナップショット・対象経路の統制観測へ結び付ける。 |
| `execution_match` | 実行観測の操作・署名対象バイト列・ポリシー・承認・最終確認が一致し、時間順序も成立することを確認する。 |
| `delegation_state` | 別の信頼鍵を使う観測者の署名から、対象チェーン・ウォレット・操作・ブロックに結び付いたコード状態を確認する。 |

操作には主体、資格情報、ワークロード、デプロイの識別情報に加え、チェーン、ウォレット、操作種別、資産、金額、送付先、calldata、委譲先、nonce、署名対象バイト列のダイジェスト、ポリシーのダイジェストを含めます。承認対象の一項目でも変更すると、元の承認を流用できません。

承認の発行後に最終失効確認を行い、その有効期間と鮮度を満たす範囲で実行を観測する必要があります。統制の観測も実行以前である必要があります。署名済みの失効や不一致は `INVALID`、承認欠落・観測不足・鮮度不足は `INDETERMINATE` と区別します。

EIP-7702 では、成功したレシートが存在しても、nonce 等が不適合な解除タプルは適用されない場合があります。逆に、後続の実行が revert しても、処理済みの委譲・解除は残り得ます。このため、レシートだけで解除を判定しません。ローカル Prague EVM で実際の認可処理とコード状態を検証し、その観測値を証跡検証にも接続します。公開チェーンには接続しません。[仕様根拠](https://eips.ethereum.org/EIPS/eip-7702#behavior)

## 保証範囲

信頼鍵と評価時刻は呼出側から与えます。鍵が別でも、運営主体や収集経路が独立している証明にはなりません。合成フィクスチャの鍵は公開テストデータで、同一プロセスで生成します。署名された観測者の陳述自体を信頼する境界が残ります。

ローカル EVM との結合テストでも、観測・評価時刻はブロック時刻から作る例示時計です。独立した時計による採取記録ではありません。統制の鮮度が範囲内でも、その期間を通じて統制が継続していたことまでは証明しません。

デプロイ権限による署名経路の迂回が観測されれば、署名整合性が正しくても統制・認可の失敗として示します。未観測の経路は不明のままです。特権コントローラーを封じ込める実装、最終確認から実行までの原子的な接続、連続的な失効監視は含みません。

`ALLOW` は検証済み証跡を受け入れる例示判定です。送金の成功、実行許可、攻撃の阻止、リプレイ防止を意味しません。消費済み操作の台帳がないため、同じ証跡は繰り返し評価できます。nonce の結合と再実行防止は別です。

v0 では、コード状態とトランザクション包含が同じブロック番号・ハッシュを示す場合に限定します。後続ブロックは祖先関係の証拠がないため不明です。reorg 対応、合意層の finality 証明、現在のグローバルなチェーン状態の独立検証はありません。汎用検証器は任意の Ethereum 署名対象データを意味解析せず、委譲先コードの安全性も保証しません。

実行方法、全入力項目、テスト、判定例は[実験 README](../../experiments/wallet-authorization-evidence/README.md)に記載しています。採択や製品組込みには、独立再現、鍵管理、実行基盤の独立した認可制御、消費済み操作の管理、チェーンの正統性・finality 等を別途評価する必要があります。
