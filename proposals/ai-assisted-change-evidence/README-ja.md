# AI支援のソフトウェア変更に関する証拠

**状態:** 参考情報としての研究提案。未採択。**確認日:** 2026年11月19日（日本時間）。
**正式な提案番号:** 未割当。**対象リリース:** 未定。
**基準:** VAP v1.2.0 Draft 3、コミット `4db6c490900dac7e85773c39bbcc5cae935bd730`。
**ライセンス:** CC BY 4.0 International。[English](README.md) · [出典レビュー](SOURCES.md)。

この提案は、特定のソフトウェア変更を、評価・承認・実行に使った証拠と結び付けるものです。
確認する問いは、**「この対象と変更前の状態に対して、この成果物は、どの試験と承認の対象であり、どの結果が観測されたか」**です。
AIが脆弱性の発見、パッチの提案、試験の作成、変更のレビューを支援した場合も同じ問いを扱います。
取得できるAIの関与を記録しても、成果物の特定や責任主体の確認が不要になるわけではありません。

FCAの11月のレビューには、条件付き承認や本番移行時の例外の記録・追跡の不備が記載されています。
DORAには、適用対象となる金融機関の変更管理に関する義務があります。
[出典レビュー](SOURCES.md)で、これらの情報とVSOによる設計上の提案を区別しています。
別途報道された11月の障害群の当事者について、責任や原因を認定するものではありません。

## 1. 提案の位置付けと対象範囲

公開やマージによって、新しいVAP要件、イベントコード、登録プロファイル、認証レベル、
標準のEvidence Pack形式が成立することはありません。VAPは事後の証拠検証の枠組みです。
[VAP §§1.3、4.5.2、4.6.3][vap]の範囲では、一般的な社内コーディングやパッチ管理を対象とする
登録済みの領域プロファイルはありません。DAPは領域プロファイルと組み合わせるcapabilityであり、
単独で適合を主張するためのものではありません。銀行がコーディング支援を使うというだけで、
取引判断を対象とするVCPの適用範囲になるわけでもありません。

モデル内部の全推論の収集、試験の十分性、全操作の捕捉、記録を改変できなくすること、
安全な配備や法令適合を保証しません。署名された説明も、説明をした主体に帰属する記述です。
観測者と検証者が評価できるのは、明示された証拠の範囲です。

## 2. 提案する証拠の結び付き

以下は**設計を検討するための語彙**です。VAPの新しいワイヤ形式や必須フィールドではありません。
実システムへの連携では、具体的な形式と信頼方針を定める必要があります。

| 工程 | 結び付ける証拠 | 確認できる範囲と限界 |
| --- | --- | --- |
| 発見・評価 | 出典・勧告、評価の版、資産の識別、観測した構成 | 当該資産との関連。CVE番号だけでは影響を受けることは確定しません。 |
| 変更 | パッチ・ビルドの原本とハッシュ、依存関係、対象、変更前の状態と構成 | 提案した成果物が同一であるか。ハッシュだけでは資産把握の正確さは分かりません。 |
| 試験 | 試験計画、対象成果物、試験環境、実行識別子・時刻、結果原本、未試験項目と範囲 | 何に対する結果か。成功していても本番環境との同等性や網羅性は別途評価が必要です。 |
| 承認 | 承認者・委任者の権限、変更証拠のハッシュ、対象、条件、期限、方針 | この操作を承認したか。条件付き承認と条件の達成を区別します。 |
| 例外 | 許容する方針、承認範囲、未達条件、理由、期限、代替措置、追跡担当 | 定めた方針で例外が許されるか。未達の試験や条件を成功に書き換えません。 |
| 実行要求・結果 | 操作・試行の識別子、要求内容、実行前の受領確認、実行先の受領証、照合記録 | 送信が許可され、実行先が何を表明したか。要求やタイムアウトは実行・未実行の証明ではありません。 |
| 健全性・復旧 | 観測対象と構成、期間、状態、ロールバックの要求と権限、復旧受領証、復旧後の観測 | 何が観測され、復旧を確認したか。復旧要求と復旧完了を区別します。 |

結果・受領証の原本は、要約やマスキング後の表示と区別して保持します。
署名主体、検証鍵を信頼する根拠、署名対象のフィールドを示します。
収集者が付けたハッシュや署名を、試験実行者や配備先の署名として扱いません。
保存・アクセス方針で保持する原文の範囲を定めます。認証情報や全プロンプトの収集を求める設計ではありません。

AIの関与については、取得できる範囲で、提供者が示すサービス・モデル名、要求・実行・ツールの識別子、
保持した観測可能な入力・出力・説明を帰属させます。これは主体を明示した観測であり、
隠れたモデル推論の取得や、実行したモデル本体の独立した証明ではありません。

## 3. 証拠の評価と実行制御

アプリケーションは、操作を許可する前に証拠を評価することができます。
その実行方針と制御はアプリケーションの責任です。VAP自体がパッチを止めたり、試験を実行したり、
緊急承認の手続やkill switchを動かしたりすることはありません。連携の設計案は次の順序です。

1. 変更、対象、変更前の状態、方針、試験証拠を正確に取り込む。
2. 証拠の結び付きと条件を評価し、その対象について承認を得る。承認された例外は例外として残す。
3. 許可判断と実行先の操作を不可分に結び付ける。成果物・対象・状態・権限が変わった場合は、方針に応じて再評価・再承認する。
4. 要求と送信状態を保存し、実行先の結果を記録する。未解決の送信は読み取り専用の照合で確認し、受領証がないことを再実行の許可と見なさない。
5. 健全性と復旧を、個別に定めた範囲と権限の下で記録する。結果不明や復旧失敗を保持する。

これは設計案であり、本番環境での不可分な実装を確立したという意味ではありません。
既存の[control-state-evidence][control]では、`preflight()`は実行許可に接続されていません。
事前評価や署名済み試験結果だけでは、確認した状態と実行時の状態の差を解消できません。

kill switchとの連携では、制御対象と版、操作権限者、訓練条件・時刻、観測した応答、保守状態、
未解決事項を結び付けることが考えられます。これは設計提案であり、FCA指定のスキーマではありません。
本作業でkill switchを実装したという主張もしません。

## 4. 結論を分けて表示する

[実験用の連携コード][experiment]では、結果の軸を分けています。

| 出力フィールド | 明示した範囲内での意味 |
| --- | --- |
| `record_integrity`（記録の整合性） | 指定した鍵の下で、提出された成果物の一覧・原文のハッシュ・マニフェストの署名を確認した。 |
| `authorization_binding`（承認との一致） | 提供された権限と承認が、要求された模擬操作を対象としている。 |
| `test_evidence`（試験証拠） | 提出した証拠が試験方針を満たす、満たさない、または判定できない。安全性の認定ではない。 |
| `approval_conditions`（承認条件） | 提出された条件の状態と参照情報が方針を満たすか。参照先は独立に検証しない。 |
| `admission`（実行許可） | ローカルの評価器が、管理された模擬書込みを許可・拒否する。VAP適合の判定ではない。 |
| `mock_execution`（模擬実行） | ハッシュを含むレコード操作について、模擬ゲートが未試行・拒否・完了確認・未解決などの送信状態を示す。 |
| `post_change_health`（変更後の健全性） | 合成の状態表明を `ATTESTED_*` として帰属させる。証拠なし・不明は `NOT_ESTABLISHED`。 |
| `rollback_evidence`（復旧証拠） | 合成の復旧表明を `ATTESTED_*` として帰属させる。証拠なし・不明は `NOT_ESTABLISHED`。 |
| `external_anchor`（外部アンカー） | このローカル実験では確立しない。 |

正しく署名された失敗試験は、整合性の検証に通っても試験方針を満たしません。
正しい実行受領証があっても、サービスは不健全な状態でありえます。
署名や提出された項目の一覧が整合していても、現実の全事象を収集できたとは限りません。

## 5. 実験との関係と残る作業

[連携実験][experiment]は、既存の[pre-record-gate][gate]を読み込んで使います。
既存ゲートの操作は `sandbox/records` に対する `create_record` です。
変更証拠のハッシュをこの模擬操作へ渡し、受領証で模擬レコードの受理を確認します。
**パッチをインストールした証明ではありません。** 実装した範囲は実験のREADMEと実行可能なテストで定めます。
マニフェストは、提出されたUTF-8の発見情報・パッチ・変更前状態・環境・試験計画・試験実行・条件の
各成果物を結び付けます。宣言した方針に従って、必要な試験の成功、結果の新しさ、対象・変更前状態の一致、
提出された条件の状態を確認してから、管理された模擬操作へ進みます。
条件証拠の参照情報が空でないことは確認しますが、その参照先の取得や独立検証は行いません。
承認はマニフェストのハッシュを含む操作に結び付きます。
未対応の緊急例外は拒否します。第2節の詳細な例外設計は提案段階です。

企業の権限管理、本番状態の観測、kill switchの証拠など、この提案が扱う広い範囲は設計上の検討事項です。
合成の健全性・復旧観測があっても、実際の配備や復旧が行われた証明にはなりません。

連携コードの方針は、その管理された入口を通る呼出しだけに適用されます。
変更していない下位ゲートは、この試験・条件の方針を評価しません。下位ゲートを直接呼ぶと、
連携コードが変更証拠を拒否していても、署名された模擬操作を書き込めます。
`bypass-companion` ケースは、この限界を明示します。回避不能な本番の実行制御を確立したわけではなく、
評価が拒否だったことを、別経路でも書込みがなかった証拠として扱えません。

既存ゲートには、ローカルでの要求・送信記録、合成の権限確認、模擬実行先の受領証、読み取り専用の照合があります。
ただし、ハーネス・時計・鍵・実行先は同一運用者の管理下です。
独立した来歴、継続的な失効確認、信頼できるUTC、外部アンカー、本番のセキュリティ境界を確立しません。

検証候補には、試験後の成果物差替え、環境・変更前状態の不一致、古い試験、未達の承認条件、
失効・期限切れの権限、記録先停止、応答消失、復旧結果不明があります。
実装したケースと実行結果は、その実験の版に結び付く記録を参照します。
過去の固定済み実行や証拠を、新しいケースの実行結果として扱い直しません。

実サービスへ進める際は、対象のAPI契約、企業内の本人・権限確認、独立した収集または明示した信頼前提、
実行制御の境界、鍵・保存管理、実行先と合意した回復動作を検証する必要があります。
実行先で何が起きたかと、そのログや運用者が何を述べたかを区別して確認します。
