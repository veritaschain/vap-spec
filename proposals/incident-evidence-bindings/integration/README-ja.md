## 1. この資料でできること

元の提案、オフライン評価、ローカル操作の実験、保存済み証拠の再検証を対応付け、
どこに実行記録があり、どの条件がまだ確認できていないかを調べられます。
次の段階として、範囲を限定した外部レビューと、その後の導入試験を提案します。
この資料の公開によって、外部レビューの依頼や実施が完了したことにはなりません。

| 段階 | 既存の成果 | 確認できる範囲 |
| --- | --- | --- |
| 事件の整理 | [事実台帳](../INCIDENTS.md) | 出典に基づく記述と、公表情報から確認できない事項 |
| 改善案 | [元の23ケース][catalogue] | 仮定した入力と、求めるアプリケーション側の判断 |
| 判断ロジック | [オフライン評価の結果][assessor] | 構造化した合成入力23件と、指定された期待値の一致 |
| ローカル操作 | [送信17件][upload]・[公開18件][publication]・[削除18件][erasure] | ローカルHTTP通信、ファイル公開、限定されたファイル削除の観測 |
| 保存と再検証 | [固定キット][kit] | 保存済み53ケースの署名、対応関係、元の記録の再検証 |

**23件と53件は別の段階の数です。53件のローカル実験だけで、元の23ケースの全条件を
実運用で満たしたとは判断できません。** 元のカタログにある未実行の表示は、提案を
公開した当時の記録として残し、後の実行結果は別の来歴で参照します。
三つのパイロットは別々の実験です。送信側の受信プログラムは測定値と受領記録を保持し、
削除側は別のローカル保存領域を使います。送信・保持・削除を一つにつないだ実証にはなっていません。

PR36の[記録済みCI][ci]では、Python 3.12.15と3.14.9の両方で37テストと53ケースの
再検証が完了しています。これは同じ開発管理主体による過去の実行結果です。
今回の文書整理で新しく実施した試験や、独立した再現とは扱いません。

## 2. 事件から読み取る設計上の課題

Bayviewについて報道が裏付けるのは、未承認の送信と事業者への削除要請です。
全監査ログの不存在や事業者側の完全削除は確認できず、病院の通知原文も独立には
取得できていません。[報道資料][bayview]

Dartmouthの委員会は企業向けClaudeのログを確認していました。個人アカウントの
未提供ログ、開示を要求する規程、AI使用そのものを禁じる規程、規程変更などにより
違反を確定できなかった事例を区別しています。[委員会報告書・2〜5頁][dartmouth]

ここから、送信対象・権限・適用範囲を結び付け、最終提出物と開示・適用規程を
対応させるという設計上の提案を導いています。両機関の制御構成を認定するものでも、
この実装なら事件を必ず防げたとするものでもありません。詳しい事実と訂正は
[事実台帳](../INCIDENTS.md)に残しています。

添付された背景メモは観測範囲や過大な法的主張を点検するための論点として読みました。
メモ中の過去のニュース、規制日程、市場数値、旧引用IDは、この資料の新たな事実の
根拠には採用していません。

## 3. 導入前に埋める必要がある差

PR36時点の全23ケースの根拠と差分は[詳細対応表](COVERAGE.md)と[JSON](coverage-map.json)にあります。
特にUP-08の行は元の送信パイロットを対象とし、その後の収集基盤の実験を評価したものではありません。
導入試験の証拠を選ぶ際には、次の基準時点の違いも確認します。

| 元の問い | 既存の関連実験 | 追加で確認すること |
| --- | --- | --- |
| UP-05 / UP-07：拒否と迂回経路 | UL-14で管理経路の外から直接送信 | 組織内の対象経路と除外経路、各経路の権限・観測範囲。観測した迂回と未観測の可能性を区別する |
| UP-08：収集基盤が停止した場合 | UL-06でローカル記録の失敗を注入 | 実際の収集先の停止、応答喪失、復旧。現パイロットのrequire_collectorはfalse |
| PB-04：図表・コードのAI利用開示 | LP-17で記録された文章への支援の記載漏れを検出 | 図表、コード、補足資料の版と開示。現パイロットは文章のみ |
| PB-07：提出先の受領・受理 | LP-14でローカル出力が見えても結果不明を保持 | 提出先への通信、提出物・開示の受領証、編集上の受理。それぞれを区別する |
| ER-05：独立した削除確認 | LE-01 / LE-18で観測と事業者主張を区別 | 別主体が管理する環境・方法・証拠による、範囲を限定した評価 |
| IR-01 / IR-02 / XR-01 | オフライン評価のみ | 情報照会の実通信、最低限の証拠保存ができない場合を含む封じ込めと欠落記録、別主体のアンカーを伴う照合 |

関連する実験があることは、要件全体を確認したことを意味しません。ローカル操作の
状態とオフライン評価の状態が異なる場合も、両方の意味を残します。

## 4. 外部レビューへ渡せる範囲

最初の依頼範囲は、**保存済み証拠の再検証**に限定できます。レビューする人が、
自分で信頼するソースと期待ハッシュを取得し、自分の環境で再検証して結果を残します。
[外部レビュー手順](EXTERNAL-REVIEW.md)には固定した対象、確認する反例、返却する証拠、
失敗した場合の扱いを記載し、[回答様式](external-review-template.json)は未記入のまま用意しています。

次の三つは別の作業です。

1. **保存済み証拠の再検証**：元の送信・公開・削除を実行せず、提供された証拠を検証する。
2. **新しい合成実験の実行**：レビューする人の環境で元のパイロットを動かし、新しい記録を取る。
   鍵や時刻が変わるため、古い証拠のハッシュとの一致を要求しない。
3. **導入環境の評価**：実際の経路、テナント、権限、保管範囲を定め、別途認められた対象で
   その主張に必要な観測を取る。

まず、どの作業をするかを記録します。独立に行われた再検証はその範囲の結果になり得ますが、
外部実装、完全削除、法令遵守、VAP適合性へ自動的に読み替えません。

## 5. 次の導入試験の順序

優先順位は設計上の提案です。

- **最初に送信経路と収集基盤を確認する。** 一つの経路・テナントを決め、許可、拒否、
  内容変更、別テナント、収集停止、応答喪失、復旧、認められた迂回試験を対応する証拠で確認する。
- **次に提出物と削除対象の範囲を広げる。** 図表・コード・補足資料を含む版管理と開示、
  提出先の受領、送信した内容と実際に保存されたオブジェクトの版・削除要求との対応、
  事業者の削除範囲、除外コピー、後から確認された矛盾を扱う。
- **その後、情報照会・証拠保存・鍵とアンカーの運用を確認する。** 作業ごとの責任、
  鍵の管理・更新・失効、証拠へのアクセス、外部アンカーの検証を、導入環境の観測で裏付ける。

各試験で、主張、許可された環境、期待する観測、失敗条件、保存する証拠を先に記録します。
不一致を見てから期待値を差し替える場合は、以前の結果を残して別の改訂として扱います。
確認できない依存先や矛盾も、そのまま結果に含めます。

## 6. この引き継ぎで確定しないこと

外部の依頼先・導入先は選定しておらず、メールや招待も送信していません。
独立した第三者による結果、本人の同意、証拠の受理は記入済みの事実にしていません。

[既存の集計基準案][counting]は、引き続き未採択の案です。独立性を主張する際は、
対象の構築・実行への関与、環境の管理、結論の変更・承認権限、金銭・契約関係の
4点を結果と一緒に示す必要があります。社内CI、鍵やプロセスの分離、この資料の公開だけで
これらの関係は解決しません。

この資料によって、規範仕様・固定証拠・実行ソースの意味は変わりません。
適合性、法令遵守、完全削除、すべてのAI利用の特定、本番運用への準備完了は確立していません。

## 7. 保持条件の追補 — 2026年10月31日 JST

[PR40の保持条件アダプター][retention-adapter]は、既存の削除証拠評価を変更せず、
別バージョンのオフライン評価を追加したものです。[保存された内部実行記録][retention-results]には、
ソフトウェアのテスト42件、期待値と一致した合成シナリオ16件、保存済み証拠の再評価16件が
記録されています。これらはアダプターのために実行した過去の記録であり、今回の引き継ぎ文書の
更新で再実行した結果や、外部レビューの結果ではありません。16件は別の合成入力群です。
固定53件に追加された操作や、元の23ケースのカタログへの追加としては数えません。

| 実装された評価 | 引き続き残る範囲の限界 |
| --- | --- |
| 処理場所、学習利用、保持条件、削除証拠の申告を分離する | 申告だけで実際の処理場所、学習利用、送信権限を独立に確定しない |
| 明示されたタイムゾーン付き期限と評価時点を比較し、不明な条件や例外を保持する | 期限到来で削除完了とは判定せず、不明な起算点や日数の計算規則を推定しない |
| リクエスト・保存場所ごとに削除申告を照合し、後日の存在申告や複数条件を残す | 事業者や収集者の申告だけで外部保存領域の実測や独立レビューは成立しない |
| 保存した署名付き入力から判定全体を再計算する | 同梱された信頼設定とハッシュによる整合確認は、外部の身元・時刻の信頼根拠にはならない |

導入環境では、実際に送信した内容を保存オブジェクトと版に結び付け、事業者の条件と応答の
出所を確認し、実際の本人確認・権限・時刻の前提を確立する必要があります。保存場所と例外の
観測、範囲を限定した独立評価には、それぞれ固有の方法・証拠・評価者が必要です。
このアダプターによって、以前の実験が一つの送信・保持・削除の観測に接続されたわけではありません。

PR40のソース時点にある保存済み16ケースには、[保持条件の別レビュー手順](RETENTION-REVIEW.md)を
使います。対象ソース、summaryのハッシュ、コマンド、期待する観測、実行後に記録する情報を
分けて示しています。PR36用の未記入の回答様式には別のアーカイブハッシュが入っているため、
この16ケースの対象記録へ流用しません。実際の観測と評価者の結論は、作成者の過去の結果や
期待する出力から区別して残します。
