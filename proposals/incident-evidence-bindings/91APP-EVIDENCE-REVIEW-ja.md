# 91APP：認証情報の侵害後に、何を証跡で確認するか

**状態：** 情報提供用・未採択の設計ノート。**出典確認日：** 2026-11-01。
**言語：** 日本語 · [English](91APP-EVIDENCE-REVIEW.md)。

このノートは、公表情報を既存の[事故由来の証跡設計案](README.md)に対応付けます。
新しい規範イベント、フィールド、プロファイル、適合性の主張は追加しません。
事件のログ、顧客データ、フォレンジック証拠一式にはアクセスしておらず、ここで参照する実験は
攻撃の再現ではありません。末尾の検討事項は、実行済みの受入試験ではありません。

## 1. 出典に基づく事実と、その限界

91APP は、システム内で ARTEX の痕跡を見つけたと説明しています。同社による侵入経路の再構成は、
Appsmith、GitLab 内の認証情報、注文データベースを経由するものです。[A1] 10月29日に公表した影響範囲は、
流出を全件確認した人数ではなく、影響の可能性がある最大の対象範囲です。[A2] 台湾の主管機関は10月20日の
告知で一部データの不正取得を確認し、その時点では詳しい種類を調査中と説明していました。同告知は ARTEX
への帰属や、その最大人数を確定した資料ではありません。[A3]

[事実台帳](INCIDENTS.md#91app)に、日付、人数、通知計画、補償に関する報道の意味、未確定の帰属を
出典ごとに記載しています。ツールの痕跡だけでは、全工程の自律実行や別事件と同一の攻撃者であることは
確定しません。確認資料から特定の CVE は確定しておらず、正確なソフトウェア版や生のフォレンジック証拠も
調べていません。[A1][A2][A3] 通知計画は、条件と公表時点を伴う会社側の説明として扱います。[A5]

以下は今後の検証設計についての分析です。91APP が実装していた管理策の説明でも、VAP が侵入を
防げたはずだという主張でもありません。

## 2. VAP と VCP に関して言えること

[リポジトリの説明](../../README.md)では、VAP は分野横断の枠組み、VCP は金融・アルゴリズム取引向けの
プロファイルです。EC の複数システムにまたがる事件は、一般的な証跡の対応付けを考える材料になりますが、
それだけで VCP の金融取引用途になるわけではありません。記録の整合性を確認する仕組みを転用する場合も、
用途との対応と検証方針を明示する必要があります。

防御側の収集は、攻撃者が VAP に参加し、操作に署名し、プロンプトやモデル判断を開示することを前提に
できません。Appsmith、GitLab、DB、外向き通信の収集者が記録できるのは、それぞれの範囲で観測した操作です。
その相関から、攻撃者の意図、隠れたエージェントの推論、全工程の自律性まで復元することはできません。

整合性の検証は、提示された記録が信頼する署名やコミットメントと一致するかを確認する助けになります。
それだけでは収集者の説明の真実性、操作の認可、ソフトウェアの脆弱性修正、管理経路を通らない DB 接続の
阻止は成立しません。[提案 §2](README.md#2-enforcement-and-evidence-have-separate-responsibilities)が示す、
実行を制御する仕組みと証跡を観測する仕組みへの依存を残す必要があります。

## 3. 今後の接続で区別すべき情報

以下はアプリケーション設計上の検討事項であり、新しいスキーマ要件や事件についての認定ではありません。

| 確認する問い | 分けて扱う証拠 | 残すべき限界 |
| --- | --- | --- |
| 認証情報が受理されたか。その操作は認可されていたか | DB の認証・権限、検証したセッション、実行主体、目的、対象、別途の承認、実行時のポリシー版 | DB 認証の成功は所有者の意思を証明しない。証跡の署名が正しいことは別の暗号的な検査であり、DB 操作の認可ではない。 |
| どの認証情報・署名鍵が、いつ有効だったか | 保護した認証情報の参照と版、発行元、権限、侵害時期の不確実性、失効決定・発効・反映の観測時刻、継続中のセッションやキャッシュ | DB の秘密情報と証跡署名鍵は信頼上の役割が異なる。更新した事実だけでは侵害開始時刻や全接続の停止は確定しない。 |
| どのデータが実際に動いたか | クエリ実行、返却対象、クライアントでの受信、書き出し、外向き通信、宛先の受領確認を、それぞれの範囲・時刻に結び付ける | 認証成功だけでは読取り、読取りだけでは書き出し、書き出しだけでは送達を確定できない。受領確認も、その後の全処理を証明しない。 |
| システム間をどう関連付けるか | 情報源の識別、保護したセッション・対象参照、照合規則、時計の誤差、不一致、別の説明の可能性 | 識別子と時系列の一致は経路の仮説を支えるが、因果関係、攻撃者の身元、自律実行の自動的な証明にはならない。 |
| 収集の対象範囲はどこまでか | 経路、アカウント、テナント、期間、収集停止、保存切れ、ゲートを迂回する経路 | 記録がなければ対象外経路の活動は未確定。別の観測が欠けていても、確認済みの不正読取り・外部送信は記録に残す。 |
| 誰が証跡や信頼設定を変更できるか | 収集者、署名者、鍵管理者、信頼設定、witness の管理境界と、利用できる独立保護された checkpoint | 同じ侵害された管理者の配下にある複数サービス・複数鍵は、独立した観測者ではない。相関だけでは TRC-005 XREF は成立しない。 |
| 封じ込めによって何が変わったか | 認可された操作と実結果、新しい構成世代、失効、変更後の限定された確認、可能だった保全と欠落 | 修復の依頼記録は完了証拠ではない。以前の評価は変更後の管理策を保証せず、後日の anchor は過去の欠落を回復しない。 |

### 認可と時刻

将来の検証器では、明示した信頼・侵害時の方針に従って署名を評価し、操作の認可を別に評価する必要が
あります。真正な記録が、不正な操作を正確に記録している場合もあります。反対に、署名鍵や DB 認証情報を
持っていることを、侵害されていない本人が操作を承認した証拠にしてはいけません。

事故調査では、失効を決めた時刻、発効を意図した時刻、各制御点が実際に適用した時刻を分けます。
観測時刻と不確実性も、主張されている出来事の時刻と区別します。自己申告の時刻だけでは過去の鍵の有効性は
確定しません。侵害期間が分からなければ、その不確実性を
残し、方針を示さずに古い署名をすべて信頼したり、すべて無効にしたりしません。長時間クエリの前の確認だけで、
その後の読取りや書き出し中も継続して認可されていたとは言えません。

### 観測と独立した確認

提案の[共通の対応情報](README.md#3-common-binding-information)と
[転送の議論](README.md#4-transfer-authorization-and-observed-egress)は、判断と実際の効果を分けます。
別の収集者が停止していても、既に確認した違反・矛盾は残します。迂回の有無を解決する観測がなければ、
欠落として記し、転送が起きたとも起きなかったとも断定しません。

独立した witness には説明可能な管理・信頼境界が必要で、別のプロセス名だけでは足りません。
真正な外部の説明は、XREF に必要な独立した対応記録・anchor・照合規則が成立していなくても参考になります。
検討者は、出典側の主張、実測した観測、そこからの推論のどれに結論が依存するかを示す必要があります。

### 個人情報と証跡保全

[提案 §8](README.md#8-privacy-and-investigation-packaging)を証跡自体にも適用します。公開する証明資料へ、
顧客の生データ、API キー、トークン、DB 接続文字列を入れません。不透明な認証情報・対象参照、保護された
対応表、権限のある最小限の開示を使います。推測可能な識別子の公開ハッシュは匿名化ではありません。
アクセス、保存、検証のために機微なコミットメントを開示する手順を記録します。

正当な緊急封じ込めを遅らせず、可能な範囲で必要最小限の証拠を保全します。得られなかった資料と、その
情報源・時刻の限界を記録します。新しい説明に署名することで失われた過去の観測を再構成した扱いにせず、
後の訂正は日付を付けた新しい記録として残します。

## 4. 既存の実験と、その境界

確認したソースは、`vap-spec` main `a2a9f6a25906db4be23e6ecd3796eab144d9ac99` と
`evidect-site` main `eeeacf7effc8103276106dcf606b2bafb7349081` です。以下は既存の first-party 実験への
参照であり、このノートのために新しく実行した試験結果ではありません。

| 既存の資料 | 関係する動作 | 成立しない主張 |
| --- | --- | --- |
| [オフライン評価器](../../experiments/incident-evidence-assessor/README.md)：`UP-05`、`UP-07`、`UP-08`、`IR-02`、`XR-01` | 拒否と実送信、未観測経路、収集停止、保全の欠落、取り込んだ外部説明を区別 | 構造化した合成入力の評価であり、本番通信、DB 操作、91APP 事件の調査ではない。 |
| [collector pilot](../../experiments/incident-collector-pilot/README.md) | 実際のローカル収集者・受取側、直前のゲート確認、限定経路の payload 到達を測定 | 同じ管理主体の loopback 実験。本番の鍵失効サービスや全経路制御はなく、最終判断と後の送信を一つの原子的観測にはしていない。 |
| [EVIDECT 実行ゲート][gate] | メモリ上のマーカー追加の直前に、要求・主体・承認者の失効、ポリシー、範囲、承認を再確認 | ID・時刻・失効状態は信頼側の合成入力。本番の認証 adapter や、直接 DB 経路がこのゲートを必ず通る保証はない。 |
| [EVIDECT 管理策再評価][revalidation] | 過去の署名を残し、構成・世代変更後は再評価を要求 | 管理策の観測値は合成値であり、認証・アクセス・検知を実測する試験ではない。 |
| [EVIDECT 受取側 witness][witness] | 新しい challenge で、受取状態と別保存された署名状態を照合 | 両保存先は同じ管理主体で、両方を巻き戻すと検出できない場合がある。独立した本番 witness や信頼時刻のサービスではない。 |

既存の試験入口は各 README に記載されています。評価器は `python -m unittest discover -s tests -v`、
collector は `python -W error::ResourceWarning run_tests.py`、EVIDECT は
`node --test examples/execution-authorization/gate.test.mjs`、
`node --test examples/control-revalidation/demo.test.mjs` と、
`examples/receiver-witness/test_*.py` の二つの入口です。それぞれの作業ディレクトリと実行環境に従います。
否定ケースの成功は、期待した拒否や不確実性が観測されたという意味であり、拒否・未確定・事件そのものが
総合的に認可成功になったことを意味しません。

[23件の catalogue](acceptance-cases.json)、元の53シナリオの証拠、後の凍結された capture は別に保持し、
変更しません。このノートは実験や署名済み記録の変更を追加せず、提案・first-party の実証を採択済み標準へ
格上げするものではありません。

## 5. 別途認可した将来の pilot に進む前の問い

1. どの実サービスが操作ごとの承認を強制し、それを通らずに DB へ接続できる経路があるか。
2. クエリの返却データと外部への送達を、どの情報源が独立に観測し、どこに欠落があるか。
3. 認証情報の侵害、失効の反映、認可キャッシュ、継続中のセッションをどう観測するか。
4. アプリ管理者が侵害されたとき、収集者、署名鍵、現在のポリシー、witness を誰が保護するか。
5. 確認済みの不正活動と未確定の観測範囲を、秘密情報・個人情報を公開せずにどう併記するか。
6. 実運用について主張する前に、別途認可したどの測定と独立レビューが必要か。

これらは検討事項であり、実装済みの受入試験や、第三者システムを試験する依頼ではありません。
