## 保存内容と由来

| 保存先 | 内容と範囲 |
| --- | --- |
| `original/` | 元のZIPと、署名付き証拠の元のバイト列をhexで含む公開2ファイル全体 |
| `github/` | 実行・ジョブ・成果物のメタデータ、および対象ジョブのデコード済みログ全文 |
| `source/` | 固定コミットと同じ10ファイル。生成コード、検証器とその依存コード、当時の依存宣言、ワークフロー、ライセンス。リポジトリ全体ではありません |
| [preservation.json](preservation.json) | 識別情報、サイズ、SHA-256、Git blob ID、当時の環境、検証範囲、限界 |
| [SHA256SUMS](SHA256SUMS) | マニフェスト自身を除いた保存物全ファイルのハッシュ |
| [verify.py](verify.py) | 保存した検証関数を使う追加の再検査。決済デモは実行しません |
| [requirements-recheck.txt](requirements-recheck.txt) | 元のジョブに記録された依存版。パッケージのバイナリ自体は含みません |

GitHubのJSONとログは、コネクターが返したデコード済みテキストをUTF-8で保存したものです。
HTTP転送時の原本バイト列や、独立署名付きの由来証明ではありません。ソースは固定したGit版から取得し、
Git blob IDと照合しました。ローカルの再検査は保存済みのIDとハッシュを検査しますが、GitHubへ接続して
元のコミットの正当性を認証するものではありません。

使用前に、別途信頼できる経路で得た配布コミットやハッシュと照合してください。マニフェストと証拠を
一緒に変更すれば、両者の整合性だけは維持できます。元の成果物にある公開鍵は同じ制御者の宣言であり、
外部の本人確認や信頼の根拠にはなりません。

## サービスを起動せず再検査する

`source/.github/` を含むディレクトリ全体を用意します。仮想環境と再検査の出力は、この保存物の
**外側**に置いてください。検査器は変更・欠落だけでなく、想定外のファイル追加も拒否します。
Python 3.12を用い、リポジトリのルートから実行する例です。

```sh
VAP_PAYMENT_ARCHIVE=research-distribution/2026-11-06-payment-collector
(cd "$VAP_PAYMENT_ARCHIVE" && sha256sum --check SHA256SUMS)
python3.12 -m venv /tmp/vap-payment-recheck-venv
/tmp/vap-payment-recheck-venv/bin/python -m pip install -r "$VAP_PAYMENT_ARCHIVE/requirements-recheck.txt"
/tmp/vap-payment-recheck-venv/bin/python "$VAP_PAYMENT_ARCHIVE/verify.py"
/tmp/vap-payment-recheck-venv/bin/python -O "$VAP_PAYMENT_ARCHIVE/verify.py"
```

依存のインストールには通信が必要な場合があります。切断する前に準備するか、準備済みの環境を使います。
再検査の2コマンドは、この保存ディレクトリと導入済み依存だけで実行できます。残りのリポジトリ、Git、
GitHub接続、サービスDB、秘密鍵、ソケット、子プロセスは不要です。監査フックで検証中の意図しない
ソケット作成や子プロセス実行を拒否しますが、OSによる隔離ではありません。

成功時は終了コード0で `PRESERVED_EVIDENCE_RECHECKED` を返し、5シナリオ・13段階、元の承認判定記録5件、
提供者受領証3件、保存済み保全観測10件の再検査を報告します。失敗時は非ゼロの終了コードと
`RECHECK_FAILED` を返します。検査対象は次のとおりです。

- 全ファイルの一覧とハッシュ、元のZIPのハッシュと展開内容一致、ソースのハッシュとblob ID、
  取得した実行・ジョブ・成果物・アップロードログの対応。
- 元の合成ポリシー、状態情報、本人対応表の下での過去の承認署名と要求の対応。
- 制御者が宣言した提供者公開鍵による元の受領証署名。
- 宣言した収集者公開鍵による元のACKと読み出し署名、保持した元の証拠バイト列、記録された
  チャレンジ、識別情報、世代の対応。
- 元の5シナリオと13段階の集計と表示。送金結果、当初の事前条件、後からの保全を区別します。

保存済みチャレンジ応答の再検査は、**過去の記録の再検査**です。新しい収集者照会ではありません。
`fresh_service_execution`、`independent_trust_established`、`present_retention_established`、
`VAP_conformance_established`、`production_readiness_established` はすべて `false` を維持します。

## 当時の環境と検証範囲

保存ログにはUbuntu 24.04.5 LTS、runner image `ubuntu-24.04` の `20261101.360.1`、
Actions runner `2.338.2`、CPython `3.12.16`、`cryptography==50.0.2`、`cffi==2.1.1`、
`pycparser==3.12` が記録されています。

元のジョブは収集25試験を通常実行と最適化実行で確認し、承認20試験と基本実行28試験も通過しています。
**固有の試験は73件**であり、同じ25件の繰り返しを加えて98件とは数えません。さらに、ここに保全した
5シナリオ・13段階の公開デモを生成しています。別の事後検証器の57試験や、ほかのワークフローは
この対象ジョブの証拠には含みません。

オフライン再検査は、サービス停止、プロセス終了、ロック、通信、残高、復旧を再実行しません。
固定した実装で保存済み証拠を検査します。元の全プロセスと鍵は同じ運用者・OSユーザーの管理下です。
提供者には、管理されたラッパーの外からローカルなベアラー認証情報で接続できる経路が残っています。
過去の承認は現在の認可を表明せず、ローカルの段階区分や収集ACKは決済作用との前後関係を独立には証明しません。

OS、パッケージバイナリ、秘密のサービス設定、DBは保存していません。環境全体の固定、PAY-01〜PAY-08
すべての受入条件、継続的な保存、独立再現、本番運用可能性を確認したものではありません。
この保存物はVAPの要件や仕様リリースを追加せず、パイロットの未採択状態を維持します。
