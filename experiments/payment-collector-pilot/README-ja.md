# 決済証拠を別プロセスへ保全する管理下のパイロット

**状態：未採択の参考実験。** [English](README.md)

[模擬承認パイロット](../payment-authorization-pilot/README-ja.md)に、実際にループバックHTTPで動く
証拠収集プロセスと別のSQLiteストアを加えます。管理された送金POSTの前に元の承認判定記録を送り、
提供者の終局的な結果を確認した後に元の署名付き受領証を保全します。口座、承認、鍵、残高変化は
すべて合成した試験用です。銀行や外部サービスには接続しません。

収集先はハッシュだけでなく、対象とした証拠の元のバイト列全体を保存します。別途設定した鍵で、
その内容と決済要求を結び付けた受領証に署名します。新しいチャレンジを使った照会で、その時点の
読み出しも確認します。すべてのプロセスと鍵は同じ運用者・OSユーザーの管理下にあり、
別プロセスというだけで独立した保管やOSによる隔離が成立するわけではありません。

## 実行と確認

Python 3.12、ネイティブな子プロセス・ループバック通信を使える環境で、リポジトリのルートから実行します。

```sh
python -m pip install -r experiments/payment-collector-pilot/requirements.txt
python -W error::ResourceWarning -m unittest discover -s experiments/payment-collector-pilot/tests -v
python -O -W error::ResourceWarning -m unittest discover -s experiments/payment-collector-pilot/tests -v
python -W error::ResourceWarning -m unittest discover -s experiments/payment-authorization-pilot/tests -v
python -W error::ResourceWarning -m unittest discover -s experiments/payment-runtime-pilot/tests -v
python experiments/payment-collector-pilot/run_demo.py --output experiments/payment-collector-pilot/generated
```

[専用CI](../../.github/workflows/payment-collector-pilot.yml)は新しい試験を通常実行と最適化実行で確認し、
既存の承認・決済実行系も再検証します。公開デモの出力は `summary.json` と `evidence-bundle.json` です。
CIで保存するファイルをこの2つに限定し、秘密鍵、ベアラー認証情報、非公開設定、データベースを含めません。
サービス用の一時ファイルは非公開の権限で作成し、デモ終了時に削除します。公開成果物の保存期間は30日です。

デモは、各ケースで別々の一時ストアを使う5シナリオです。以下のPOST件数は送金用であり、
証拠収集用の通信件数と区別します。

| シナリオ | 送金結果 | 送金POST／残高作用 | 保全について確認する区別 |
|---|---|---|---|
| 正常な収集 | `SETTLED` | 1／1 | 元の送出前条件と結果証拠を保全 |
| 送信前に収集者が停止 | `UNKNOWN` | 0／0 | 後から回収しても、当初の送出前条件は成立しない |
| 収集確定後に受領応答を喪失 | `UNKNOWN` | 0／0 | 再起動後に同じ受領証を回収し、送金は再開しない |
| 提供者の確定後に応答を喪失 | `UNKNOWN` → 提供者GET後に `SETTLED` | 1／1 | 照合後に元の提供者受領証を別途保全 |
| 提供者の応答後に収集者が停止 | `SETTLED` を維持 | 1／1 | 明示的な証拠回収までは、結果証拠の保全が未確認 |

## 検証範囲

新しい試験は **25件**で、通常実行とPython最適化実行で確認します。最適化実行は同じケースの再実行です。
既存の試験は承認20件、基本実行系28件、事後証拠検証57件です。

実際のサービス停止、SQLiteロック、プロセスのSIGKILL、確定後の応答喪失、初期化を済ませた複数ワーカーの競合、
元のバイト列の保持、不正・別記録に結び付いた応答、過去と現在の観測の区別、世代更新、読めないローカル記録、
呼出し側による入力変更、事後に送出前条件を作らないことを検証します。
準備完了通知と明示的な停止点で処理順序を制御します。必要なプロセス・通信機能が使えない場合は失敗であり、
スキップや模擬的な成功には置き換えません。

応答の不正ケースは、実際の収集通信を行った**後**、信頼した試験用の受信境界でバイト列を変更・再署名します。
拒否条件の検証であり、現実のネットワーク侵害を再現したとの主張ではありません。
新しい照会で未検出になる試験は、同じ一時鍵に対して明示的に空の試験ストアを用意します。
過去と現在の区別を確認するもので、巻き戻しへの耐性を実証しません。
デモで受領応答喪失後に収集ストアを直接調べる操作も、同じ制御者による観測であり、呼出し側の認識とは区別します。

## 処理順序と使用済みにした送出機会

| 段階 | 必要な処理 | 失敗時の扱い |
|---|---|---|
| ローカル承認 | 既存の合成承認条件を検証し、元の承認判定記録と `CLAIMED` を一括確定 | 確定に失敗した呼出しは送金POSTを行わず、保存成功とも扱わない |
| 承認記録の収集 | 確定済みの元の記録を、ローカル書込トランザクションの外で収集先に送る | 収集が停止しても、確定済みの送出機会は使用済みのまま |
| 収集の事前条件 | 設定した鍵で受領証の署名と内容を照合し、新しい照会を行い、その確認をローカルに保存 | 不明、不正、内容不一致、保存失敗の場合は送金POSTへ進めない |
| 送金の試行 | 最初に使用済み記録を作った呼出しだけが、1回のPOST機会を得る | 再呼出し・復旧でこの機会を復活させない |
| 提供者の結果 | 既存の実行系で元の署名付き受領証を検証・保存 | 受領証を確認できなければ送金結果は未解決 |
| 結果証拠の収集 | 検証済みの提供者受領証を別途収集 | 収集失敗によって確認済みの `SETTLED`／`FAILED` を消さない |

送出前の拡張処理は信頼したコード設定であり、要求データに指定できる機能ではありません。
新たに確定した使用済み記録に対してのみ動作します。承認記録と使用済み記録を確定する
トランザクション中には収集先とのネットワーク通信を行いません。

ローカル記録、収集先、決済提供者をまとめた分散トランザクションはありません。
使用済み記録の確定後にプロセスが停止すると、試験側ではPOST前の停止と分かっていても、
復旧したアダプターでは結果未解決として扱います。その不確実性を保持し、送出機会を復活させません。

## 送金・承認・保全を分けて読む

`state` は既存の決済結果です。`mock_admission` は記録された合成ポリシーと提示された状態情報の下での
元の承認判定です。収集の結果は、これらと別の観測として返します。

| 観測 | 確認できること | そこからは確認できないこと |
|---|---|---|
| 元の収集受領証を検証できた | 設定した収集者の鍵が、対象バイト列の受領を表明した | 現在も稼働していること、必要な全イベントを収集したこと |
| 新しい照会で一致する記録を確認した | そのチャレンジへの応答として記録が返った | 継続的な可用性、あらゆる故障に対する保存の存続 |
| 元の送出前条件が保存されている | 管理された呼出しがPOST機会の前に収集条件を記録した | 実際にPOSTしたこと、送金が完了したこと |
| 後から承認記録を回収した | その元の記録を今保全できた | 当初の送金前に保全済みだったこと |
| 送金は `SETTLED`、結果証拠の保全は未確認 | 提供者の結果は確認済みだが、その証拠の収集確認がない | 送金失敗、または再送が必要であること |
| 新しい署名付き照会が未検出を返した | その照会時には記録が返らなかった | 過去にも存在しなかったこと、未実行、削除の証明 |

既存の `synthetic: true`、`business_authorization_verified: false`、`production_gate: false`、
`automatic_retry: false` を保持します。本番の業務認可やVAP適合をまとめて肯定する判定は追加しません。

`PRE_DISPATCH`、`POST_EFFECT`、`HISTORICAL_RECOVERY` は、ローカルの管理された処理経路が付ける区分です。
収集者が署名するのは対象バイト列の受領であり、提供者の作用に対する前後関係を独立に証明しません。
元の事前条件はローカル記録であり、ゲートが別途署名した証明ではありません。
記録を読めない場合は事前条件を `UNKNOWN` とし、照会に成功して記録がない場合に限って `NOT_RECORDED` とします。

## APIごとの作用

| `CollectedAdapter` のメソッド | ネットワーク処理 | ローカルでの意味 |
|---|---|---|
| `submit(request, evidence)` | 新規記録を作った呼出しだけが収集と1回の送金POSTへ進む。再呼出しは通信しない | 元の承認、使用済み記録、保全履歴を保持 |
| `read_status(request)` | なし | 送金結果、過去の承認、過去の保全を読む |
| `read_custody(request)` | なし | 保存済みの観測を再検証。現在の保全状態は表明しない |
| `reconcile(request)` | 未解決の使用済み記録に必要な提供者GETのみ | 結果受領証を保存。暗黙には収集しない |
| `recover_evidence(request)` | 収集先へのPOSTと新しいGETのみ | 過去の証拠の保全観測を追加。当初の事前条件は作らない |
| `check_custody(request)` | 新しいチャレンジによる収集先GETのみ | 観測を返し、送金やローカル保全記録を変更しない |

ローカルの保全読出しは直近128件を調べ、元の事前条件の観測がその外にある場合は追加して検証します。
返す観測一覧や検証不能件数はこの読出し範囲の結果であり、全履歴の一覧や完全性の証明ではありません。

## 復旧で識別子や過去の記録を書き換えない

同じ送金要求を繰り返しても、元の使用済み記録を使います。提供者との照合は送金POSTを行いません。
証拠回収は別の明示的な操作です。収集先への元の証拠の送信と照会はできますが、送金の使用済み記録を
作成・解除したり、送金送信を呼び出したりしません。

同じ要求・証拠段階・元のバイト列の収集は冪等です。再収集では元の受領証を返し、
過去の収集時刻を作り直しません。対応関係が矛盾する入力では記録を上書きできません。
承認記録と提供者の結果は別段階であり、一方の受領証をもう一方の確認には使えません。
要求に結び付いた世代や設定を更新しても、使用済みの操作ID・冪等キーはリセットしません。

基本実行系で作った古い記録には承認記録がなく、承認パイロットで作った記録には送出前の収集条件がない場合があります。
後からの回収で過去の記録を捏造せず、事後収集を送出前の保全へ格上げしません。
読み出す署名付き記録は設定された鍵で再検証し、保存済みの状態ラベルだけでは成功扱いにしません。

## 検証と信頼の限界

収集受領証は収集者、証拠段階、元の要求、保存した記録に結び付けます。読み出し応答は新しいチャレンジにも
結び付けます。再収集やプロセス再起動でも、元の受領証と証拠のバイト列を保持します。
収集者・決済提供者の公開鍵は応答の外で設定します。デモ成果物に含まれる公開鍵は同じデモ運用者の
宣言に留まり、それ自体では独立した由来を証明しません。

承認記録に対する既存の過去の整合性検査を維持します。収集したという事実によって、その記録に含まれる
ポリシー、本人対応表、承認鍵が本物の人間による承認として独立に認証されるわけではありません。
収集者は攻撃者の内部判断や、合成した役割の背後にいる実際の人物を観測しません。

承認判定は引き続き使用済み記録を作る時点のものです。収集にかかる時間は、その判定から送金作用までの
間隔を増やします。署名付き状態情報は現実の最新状態とは限らず、その間に有効期限切れや失効が起こり得ます。
最新の権威元への照会、継続的な失効の強制、承認と送金の不可分な処理は実証しません。

## 実験の範囲

**PAY-08**の収集・停止に関する問いの一部を、既存の **PAY-06** の復旧動作と合成承認につなぐ追加実験です。
[決済提案](../../proposals/payment-api-evidence/README-ja.md)は未採択で、8群すべての受入条件は未実証です。
別の57試験の事後検証器とフィクスチャは既存の役割・スキーマを維持します。
実行前の検証のために未来の決済結果を作りません。

提供者は既存のローカルなベアラー認証情報を使います。その保持者は基本アダプターや提供者へ直接接続し、
ラッパーを迂回できます。収集は管理された呼出し経路の事前条件であり、提供者側で全経路に強制する境界ではありません。
SQL制約や別プロセスは、管理者や同じユーザー権限で動くプロセスへの隔離を保証しません。

保存する完全な記録には合成した要求・承認情報が含まれます。本番のプライバシー、秘匿化、保存・削除方針、
アクセス制御の設計はありません。独立アンカー、収集全体の完全性チェックポイント、拒否ログの確実な収集、
認証された外部時計、鍵ライフサイクル、保存状態の巻き戻し・完全停電への保証、侵害根絶の証明、実銀行の決済、
独立再現、本番運用可能との主張は含みません。
