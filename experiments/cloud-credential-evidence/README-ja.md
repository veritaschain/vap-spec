# クラウド資格情報の証拠検証実験

**位置付け：未採択の参考実験。オフラインの合成データを使用。** [English](README.md)

[提案のCE-01〜CE-10](../../proposals/cloud-credential-evidence/README-ja.md)にある証拠の区別を、
範囲を限定して実行可能にする実験です。合成の収集記録、Azure形式の一部を対象にした版付きの対応規則、
呼出側から別に渡す信頼・権限設定を検査します。Azure接続、Microsoft・Todylの事件再現、
VAP適合性の成立を示すものではありません。

## 実行方法

[専用ワークフロー](../../.github/workflows/cloud-credential-evidence.yml)はPython 3.12と、
版を固定した`cryptography`を使います。リポジトリのルートから実行します。

```sh
python -m pip install -r experiments/cloud-credential-evidence/requirements.txt
python -m unittest discover -s experiments/cloud-credential-evidence/tests -v
python -O -m unittest discover -s experiments/cloud-credential-evidence/tests -v
python experiments/cloud-credential-evidence/fixtures.py
```

fixtureコマンドは合成入力を評価して、期待した証拠の区別と一致するかを検査します。
コマンドの成功はそのテスト条件との一致を意味し、操作の安全性、事件の防止、
実際のクラウド環境の監査完了を意味しません。

ライブラリの入口は`verify_bundle(bundle, trust, *, scope, evaluation_time)`です。
信頼設定、レビュー範囲、評価時点は、証拠の束とは別に呼出側が指定します。
検証器は実時計の参照、証拠の取得、クラウド要求、操作の再試行、資格情報の失効、
リソースの変更を行いません。

このディレクトリで、1件の生成例を確認できます。

```python
from cloud_evidence import verify_bundle
from fixtures import positive_case, seal_bundle

case = positive_case()
report = verify_bundle(
    seal_bundle(case), case["trust"],
    scope=case["scope"], evaluation_time=case["evaluation_time"],
)
print({name: item["status"] for name, item in report["claims"].items()})
```

CLIは別々のJSONファイルを`--bundle`、`--trust`、`--scope`で指定し、
`--at`にはUTCのUnix時刻を整数で渡します。実験では`synthetic: true`が必須です。
JSONの対応範囲は限定しており、重複キー、小数・非有限値、負のゼロ、NFCでない文字列、
過大な階層・容量を拒否します。一般的なAzure出力デコーダーではなく、
未対応の出典形式を黙って書き換えません。

## 別々に評価する問い

結果は実験用の`supported`（裏付けあり）、`contradicted`（矛盾あり）、
`unresolved`（未解決）を使います。裏付けは呼出側の信頼設定と提出範囲に条件付きです。
確認できる矛盾は、無関係な証拠が不足していても保持します。
全体の安全判定、実行許可、認証、規範上のVAP判定は出しません。

CLIは**評価結果を出力できた場合に終了コード0**を返します。矛盾や未解決を含む場合も同じです。
**入力・設定の形式が不正な場合は2**を返します。終了コードを操作の実行許可として使わないでください。

| 問い | 判定の範囲 |
| --- | --- |
| 署名と由来 | 署名したバイト列を検証した後、その鍵が対象の発行者・役割・テナント・リソースについて、当該時点で記述する権限を持つかを別に確認する。 |
| 認証と操作権限 | 認証成功と、正確な操作を対象にした許可・有効期間を区別する。 |
| リソースの観測 | 対応する出典が報告したSecretGetと、取得ペイロード・外部転送・その後の利用を区別する。 |
| 記録の関連 | 収集者が署名した対応付けは、その収集者の権限に基づく記述。同じ相関ID・IP・近い時刻だけなら関連候補にとどめる。 |
| 証拠の時刻 | 発生、出典で利用可能になった時刻、受領、評価時点を区別する。遅れた証拠を過去の前提条件に繰り上げない。 |
| 収集と封じ込め | 呼出側が宣言した記録集合・期間を評価する。収集・トークンの由来・別テナントの欠落を残し、普遍的な封じ込めとみなさない。 |
| AI利用の評価 | 出典と日付を持つ判断を保持する。Agent・UserAgent欄から攻撃者の内部判断を直接観測したとは言わない。 |

## 元の記録と収集者による補足

対応規則の根拠は、提案の[出典台帳](../../proposals/cloud-credential-evidence/SOURCES.md)を参照してください。
対象は制限した形式であり、すべてのAzure出力やクラウドサービスを解釈する実装ではありません。

元のUTF-8記録のバイト列とコミットメントは、正規化した表示と別に扱います。
検証器がコミットメントを再計算し、表示を元データから導きます。提出側が書いた正規化値で
原本の意味を置き換えることはできません。元の記録にない事実は不明のまま残します。

認証ログのワークスペース`TenantId`と、`AADTenantId`、`AppOwnerTenantId`、
`ResourceOwnerTenantId`を区別します。Key Vaultの`resourceId`はVaultを指し、
正確な要求URIは別途対応付けます。`resultSignature`という名前の項目を
Azureの暗号署名とは扱いません。結果項目は、出典ごとの意味で解釈します。

メソッド、APIの制御系／データ系、試行の正確な対応を、元の記録にないまま補いません。
使用する場合は、収集者や要求観測側による別の署名付き補足として明示します。
これは設定した署名者の記述であり、クラウド事業者が発行した因果関係の証明ではありません。
元の記録への参照、操作名、API版、結果を照合し、後の再試行の成功を先の失敗へ移し替えない設計です。

[Get SecretのREST仕様](https://learn.microsoft.com/en-us/rest/api/keyvault/secrets/get-secret/get-secret?view=rest-keyvault-secrets-2025-07-01)は、
読出し成功をGETとHTTP 200で説明しています。検証器は収集者の補足に明示された矛盾するメソッドを検出し、
HTTP 202・204をSecretGetの読出し成功と判定しません。メソッドの情報がない場合は不明のまま保持し、
元の記録にGETを補いません。

## 信頼と解釈の前提

- 証拠の束から、信頼する鍵を追加したり、呼出側の権限設定を広げたりできません。
- 鍵の権限は名前だけで決めず、発行者、役割、テナント、リソース、有効期間で限定します。
- 署名の数学的な正当性と、信頼できる由来を別に報告します。収集者の署名が保護するのは
  収集者の記述です。Azure由来、誠実な収集、正確な出典の時計、未観測の活動までの完全性は別の問題です。
- レビュー範囲は操作、試行、主体、Vault、正確な要求URI、対象API、操作種別、期間、期待する証拠集合を指定します。
  同じAppIdだけで欠けた対応を補いません。
- 認証先リソースのID、所有テナント、リソースのサービスプリンシパルも呼出側が指定します。
  出典のGUIDとOAuthのaudienceが同じ識別子だとは仮定しません。
- 鍵の権限期間は、記録が主張する受領時刻について検査します。実際の署名時刻、鍵の履歴、
  主張された時計の正しさまでは証明できません。
- JSONと署名の形式は実験固有であり、RFC 8785やVAPのワイヤー形式ではありません。原本には別のバイト列コミットメントがあります。
- fixtureの署名用seedは公開を前提にした合成データです。別々の鍵を使っても、別組織や独立保管の証明にはなりません。

呼出側の`scope.action_time`は、証拠の利用可能性を調べるチェックポイントです。
`prerequisite_record_ids`で、その前に必要な認証・許可の証拠を指定します。
後から届く操作結果や収集記録は事前条件にしません。観測された操作への許可の有効性は、
その操作の元イベント時刻と照合します。操作時刻が不明なら、事後の認可評価も確定できません。

エンベロープの時刻はUTCのUnix秒を整数で指定します。対応する元のUTC時刻は小数点以下7桁まで
比較時に保持します。順序の検査は指定された時計を前提とし、信頼できる時刻認証ではありません。
発生・利用可能・受領の順序矛盾はチェックポイントの判定とは別に残し、
未来まで続く収集期間を終了済みとは判定しません。

対応付け、収集記録、出典評価の改訂が正確なエンベロープを参照するときは、受領順序も確認します。
参照先のエンベロープを受領する前に、それを参照するエンベロープを受領したとは判定しません。
これは比較可能な受領時計を仮定した検査です。出典の発生・利用可能時刻は元の観測についての時刻であり、
後から包んだ記録全体の署名・公開時刻ではありません。事後に結び付けた記録は後から受領できますが、
署名時刻や包んだ記録全体の公開時刻を証明するものではありません。

## 受入ケースとの対応

10個の識別子は提案上のグループであり、実事件の件数や、本番アダプターの全要件が完成したことを意味しません。
意味上の矛盾を入れた後に署名し直すテストも含め、署名が正しくても結び付けの変更を検出することを確認します。

| グループ | 実行して区別すること |
| --- | --- |
| CE-01 | 一致する証拠でも、対象の操作と宣言した収集範囲に限って裏付ける。 |
| CE-02 | 認証成功、利用・許可の証拠不足、明示的な拒否を分ける。 |
| CE-03 | 同じAppIdやワークスペースIDで、テナント内の主体や権限をまとめない。 |
| CE-04 | 署名の正当性だけで、発行者・役割・テナント・リソースへの権限を補わない。 |
| CE-05 | 弱い関連は候補として保持し、正確な結び付けの不足や矛盾を残す。 |
| CE-06 | メタデータの取得成功と、出典が報告した秘密の内容取得を分ける。 |
| CE-07 | 遅延した証拠、利用可能性・受領が不明な証拠で、事前の利用を裏付けない。 |
| CE-08 | 失敗と、要求を変えた再試行の対応・結果をそれぞれ保持する。 |
| CE-09 | ローテーションや範囲付き検索で、トークン・テナント・期間全体の封じ込めを確定しない。 |
| CE-10 | 初期と更新後の出典評価を残し、エージェントのラベルから内部判断を作らない。 |

## 残る実装上の範囲

別の[ローカル収集パイロット](../cloud-credential-collector/README-ja.md)が、元バイト列の保管、
署名付き収集受領書、プロセス停止からの回復テスト、元記録エンベロープの出力を追加します。
本検証器の判定規則は維持します。実際のローカル受領時刻をそのまま受領時刻として扱い、
出典の利用可能性、権限、正確な操作の対応、収集の終了確認を接続処理で作りません。
そのローカル署名とチェックポイント比較だけでは、Azure由来や独立保管は成立しません。

このディレクトリは、オフラインで証拠の意味を再検査できる実験です。
実環境のAzure収集器、資格情報保管、API接続、完全なクラウド形式のデコーダー、実行時の認可ゲートは含みません。
実事件の証拠データ、社外の独立実行、当事者間のアンカー、変更不能な保管サービス、
デプロイの保証、予防効果の測定も含みません。

実際の接続には、認証された収集と出典別の対応、原本保護、限定した信頼設定と鍵管理、
時計・利用可能性の測定、プライバシー・保存制御、実環境での検証が必要です。
収集しなかった証拠を後からハッシュや署名で復元することはできません。
合成fixtureには、本番の資格情報、顧客データ、取得した秘密の内容を使いません。
