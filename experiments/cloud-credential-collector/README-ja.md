# クラウド証拠のローカル収集パイロット

**位置付け：未採択の参考実験。合成テストによるローカル保管の検証。**
[English](README.md) · [証拠検証器](../cloud-credential-evidence/README-ja.md) ·
[設計提案](../../proposals/cloud-credential-evidence/README-ja.md)

手元に存在する記録ファイルを受け取り、元のバイト列を保存し、署名した収集受領書を記録します。
既存のオフライン証拠検証器に対し、実際のファイル保存、プロセスの再起動、再試行の処理を追加する実験です。
元記録のエクスポートを通じて両者を接続し、出典の利用可能時刻、権限、操作の対応関係を補って作りません。

CLIはAzureや認証付きクラウドAPIへ接続しません。取得済みファイルを持っていることと収集者の署名だけでは、
Microsoftがその記録を作ったとは確認できません。公開するデモとテストには、合成記録と公開のテスト用署名鍵だけを使います。

## 実行方法

Linux、Python 3.12、版を固定した依存ライブラリを使います。`/proc/self/fd`と
`renameat2(RENAME_NOREPLACE)`が必要で、利用できなければエラーとします。リポジトリのルートで実行します。

```sh
python -m pip install -r experiments/cloud-credential-collector/requirements.txt
python -W error::ResourceWarning -m unittest discover -s experiments/cloud-credential-collector/tests -v
python -O -W error::ResourceWarning -m unittest discover -s experiments/cloud-credential-collector/tests -v
python -W error::ResourceWarning experiments/cloud-credential-collector/run_demo.py
python experiments/cloud-credential-collector/collector.py --help
```

専用の[ワークフロー](../../.github/workflows/cloud-credential-collector.yml)はUbuntu上で確認します。
デモは一時的な非公開ファイルと実プロセスを使用し、短い結果を表示した後にテスト用の保存物を片付けます。
テストの成功が示すのは、その環境で確認した個々のローカル動作です。クラウド収集、独立保管、
電源断に対する耐久性、事件の予防を認証する結果ではありません。

### 収集コマンド

すべてのコマンドに`--store`と、呼出側が指定する`--public-key-file`を渡します。
署名するコマンドには`--private-key-file`も必要です。鍵ファイルはちょうど32バイトの生データで、
十六進テキストやPEMではありません。秘密鍵はEd25519のシードで、指定した公開鍵に対応する必要があります。
鍵ファイルは保存先の外で用意し、公開鍵を誰の鍵として信頼するかは別に確立します。

| コマンド | 追加の引数と出力 |
| --- | --- |
| `init` | `--collector-id`、`--key-id`。非公開の保存先と署名した保存先情報を作る。 |
| `collect` | `--input`、`--request-id`、`--context`。既存のローカル記録をコピーし、受領書をコミットまたは回収する。 |
| `audit` | 任意の`--checkpoint`。現在コミットされている保管状態を検証する。秘密鍵は不要。 |
| `checkpoint` | `--out`。署名したチェックポイントを新しい非公開ファイルへ書く。保存先と別に保管する責任は呼出側にある。 |
| `export-native` | `--request-id`、`--out`、任意の`--checkpoint`。保管状態を検証し、元記録のエンベロープを新しい非公開ファイルへ書く。 |

`--context`は`schema`、`adapter`、`issuer`、`tenant_id`、`resource_id`だけを持つJSONオブジェクトです。
schemaは`experimental-cloud-custody-source-context-v0`です。nativeエクスポートは既存検証器の
`azure-service-principal-signin-subset-v0`と`azure-key-vault-audit-subset-v0`に対応します。
収集時の文脈は署名した受領書に含まれ、エクスポート時に別の文脈へ付け替える引数はありません。

Python APIは`initialize_store(...)`と`Collector`コンテキストマネージャーです。
`collect_file(...)`、`get_receipt(...)`、`audit(...)`、`checkpoint()`、`export_native(...)`を使います。
合成入力での呼出例は[テスト](tests/test_collector.py)を参照してください。

CLIの終了コード**0**はローカルコマンドの完了、**2**は要求の拒否またはエラーを示します。
監査に成功しても、`completeness: unresolved`、`independent_custody: false`を返します。
`rollback_assessment`は、チェックポイントがなければ`not_assessed`、比較が一致した場合は
`consistent_with_retained_checkpoint_only`です。いずれの終了コードも、クラウド操作を実行する許可にはなりません。

## 保存と再試行

要求IDに、入力した正確なバイト列と固定した出典文脈を結び付けます。文脈は実験用アダプター、
収集者の発行者ID、テナント、リソースを指定します。これは収集者による記述であり、元の出典の身元が
自動的に確定するわけではありません。後段の証拠検証器が、文脈、元記録のフィールド、呼出側の信頼範囲を照合します。

元バイト列をコピーし、内容のハッシュを名前とする非公開ファイルに保存します。JSONの配置、空白、
改行もコミットメントの対象です。正規化した表示で原本を置き換えません。原本の保存・同期後に、
SQLiteで受領書と索引をコミットします。プロセス間の排他ロックで、保存先の検証から変更までを直列化します。

保存先は`index.sqlite3`、`store.lock`、`blobs/`、`staging/`を含み、SQLiteのロールバックジャーナルが
作られることもあります。ディレクトリのモードは`0700`、ファイルは`0600`です。
原本1件は最大65,536バイト、コミット済み受領書は最大1,024件、データベースは最大64 MiBに制限します。
無制限の一括ログ取込器ではありません。監査は未コミットの原本や作業用ファイルの数を、
コミット済み受領書と分けて報告します。それらのファイルがあるだけで収集の受理が成立するわけではありません。

| 状況 | 要求する動作 |
| --- | --- |
| 新しい要求 | バイト列と文脈を保持し、保存先ID、連番、直前の受領書のコミットメント、収集者の受領時刻を署名した受領書へ結び付ける。 |
| 同じ要求・同じバイト列・同じ文脈 | 保存先と原本を再検証し、最初の受領書と時刻を返す。 |
| 同じ要求IDでバイト列または文脈が変更された | 矛盾する再試行として拒否する。 |
| 受領書のコミット前にプロセス停止 | 受理済みの受領書は存在しない。再試行では、その時点の新しい受領時刻を記録できる。未索引の原本は、正確な一致を検証した場合に限って再利用できる。 |
| コミット後・応答前にプロセス停止 | 再起動後の再試行で、最初にコミットした受領書を回収する。 |
| 保存済み原本や索引付き受領書の消失・変更 | エラーとする。自動修復、黙った再収集、過去の受領書の置き換えはしない。 |
| 既存の保存先に初期化を再実行 | 完全な既存保存先を検証し、同じIDを保持する。一部が欠けた配置は、ファイルやディレクトリを作り直さず拒否する。 |

収集の再試行は、既に手元にある記録の保存処理をやり直します。クラウド上の操作を再送しません。
受け取らなかったデータの復元、クラウド検索の完全性、欠けたページング情報や収集期間の終了確認はできません。

## 監査・信頼・チェックポイント

監査には呼出側が与える公開鍵が必要です。保存先に書かれた鍵の名前だけで、その鍵を信頼しません。
コミット済み原本を読み直し、署名付きの保存先情報と受領書、受領書と索引の連鎖を検証します。
原本のハッシュは内容へのコミットメントであり、暗号化や出典の証明ではありません。

呼出側が別に保持した署名付きチェックポイントを指定できます。保存先ID、連番、その位置の受領書の
コミットメントを示し、比較で言える範囲を次のように限定します。

| 得られる証拠 | 監査で述べられること |
| --- | --- |
| 保存先の内部は整合しているが、外部のチェックポイントがない | 指定した信頼鍵の下で、提示されたバイト列と連鎖が整合する。巻き戻しは未評価。 |
| 現在の保存先の途中までに対応する、有効なチェックポイントが一致 | そのチェックポイントとは整合する。その後の受領書が正当に追加されていてもよい。 |
| 後の時点のチェックポイントを保持しているが、現在の保存先にその連番がない | 提示された保存先とチェックポイントが矛盾する。 |
| 別の保存先・別の連鎖・信頼されていない鍵のチェックポイント | チェックポイントとの比較を拒否する。 |

古いチェックポイントが一致しても、それより後の末尾が一度も消されなかったことは示せません。
データベースの隣に置いたチェックポイントは一緒に巻き戻せるため、独立して保管された観測にはなりません。
この実験は第三者への配信、透明性サービス、XREFのための独立記録・アンカーを実装しません。

対象とするのは、偶発的な破損、呼出側の信頼鍵や保持したチェックポイントとの比較で観測できる変更、
プロセス停止、同じ処理に従う複数収集プロセスの並行動作です。管理者や収集者の秘密鍵を持つ主体は、
環境を変更し、新たな記述を署名できます。ローカル権限、ロック、署名によってこの信頼の前提は消えません。

## 元記録のエクスポートと時刻

接続処理は保管状態を検証してから、既存検証器の署名付きnativeエンベロープを作ります。
元のUTF-8文字列とバイト列のコミットメント、収集時に固定した文脈、最初の受領時刻を引き継ぎます。
元のJSONを再シリアライズしません。対応していないバイト列や形式でも原本としての保管は可能ですが、
native形式へのエクスポートは明示的に失敗します。
nativeエンベロープはコミットメントで受領書を参照しますが、保存先や受領書の連鎖そのものは含みません。
既存の証拠検証器はエクスポートした記述を評価します。保管の監査を再実行するには、保持した保存先、
呼出側が指定する信頼済み公開鍵、比較に使うチェックポイントが別途必要です。

CLIはホストの時計から受領時刻を取得し、日時の指定や過去への変更オプションを設けません。
テストではPython APIから時計を注入できます。受領書はナノ秒精度の値を十進文字列で保持します。
既存検証器の整数秒の`received_time`へ変換するときは**切り上げ**るため、記録した受領時刻より前へ移りません。
1秒未満の保守的な遅れが加わり得ますが、これは測定した通信遅延ではありません。

エクスポートした包絡情報では、出典のイベント時刻と利用可能時刻を不明のまま残します。
既存検証器が、対応する元記録からイベント時刻を独立して読み取ります。元イベントの日時だけでは、
収集者がいつ取得できたかは分かりません。ホスト時計の正しさ、時計同期、出典の真正性には実環境の証拠が必要です。

エクスポートは、許可の記述、正確な試行への結び付け、収集の完全性、AIによる指揮の主張を作りません。
結合テストでは呼出側が別途、合成の方針と文脈を渡せます。その場合でも、操作後に受領した記録を、
操作前に利用可能だった前提条件へ繰り上げません。事後の「出典が報告した読出し」が裏付けられても、
外部への持出しの観測や完全な封じ込めまで成立するわけではありません。

## 非公開ファイルと運用上の範囲

非公開のディレクトリとファイル、読込量の上限、不適切なファイル種別やパスの別名の検査を使用します。
通常のCLI出力へ原本や秘密鍵の内容を出しません。明示的なnativeエクスポートには元記録が含まれるため、
非公開の証拠として扱う必要があります。出力先の既存ファイルは上書きしません。実際の保存先、秘密鍵、
エクスポート、顧客ログをリポジトリや公開CIの成果物へ入れないでください。

Linuxのファイルシステムとプロセスを使ったテストです。Windows対応、ネットワークファイルシステムの正しさ、
実行中に管理者がパスを差し替える攻撃への耐性、保存時暗号化、保存・削除方針、保護された署名ハードウェア、
信頼できる時刻を確立するものではありません。プロセス強制終了からの回復は、OS停止や電源断の試験とは別です。
SQLiteと明示的な同期も、ファイルシステムや機器が契約どおり動くことに依存します。
[SQLiteの原子的コミット](https://www.sqlite.org/atomiccommit.html)と
[Pythonのファイル同期](https://docs.python.org/3.12/library/os.html#os.fsync)を参照してください。

独自の保管形式を持つ追加実験です。規範的なVAPフィールドの変更、汎用クラウドプロファイルの採択、
VC-Certifiedの結果、実行時の許可制御は含みません。既存の証拠検証器の合成入力要件と判定範囲も引き続き適用します。
