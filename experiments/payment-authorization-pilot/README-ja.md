# 管理された決済承認パイロット

**状態：未採択の参考実験。** [English](README.md)

[決済実行時パイロット](../payment-runtime-pilot/README-ja.md)で新しい要求を使用済みにする前に、
合成した起票者・承認者の条件を検証します。実際のループバックHTTP、提供者側の別保存領域、
模擬残高の変化を使います。銀行、実資金、本人が操作する承認システム、外部サービスには接続しません。

運用者がポリシー、検証鍵、公開鍵と人物の対応を別途採用し、呼出し側が署名付き承認・状態情報の
元のバイト列を提示します。ゲートは正確な決済要求との対応を検証し、使用済みにする時点で判定して、
承認判定の記録と送出権の使用済み記録を同じトランザクションで保存します。
対象は管理されたアプリケーション経路です。提供者の全経路を囲む排他的なセキュリティ境界ではありません。
元の実行時アダプターは、信頼する呼出し側向けの基本処理として維持します。

## 実行方法

Python 3.12と、実際のループバック通信・プロセス操作が可能な環境で、リポジトリのルートから実行します。

```sh
python -m pip install -r experiments/payment-authorization-pilot/requirements.txt
python -W error::ResourceWarning -m unittest discover -s experiments/payment-authorization-pilot/tests -v
python -W error::ResourceWarning -m unittest discover -s experiments/payment-runtime-pilot/tests -v
python experiments/payment-authorization-pilot/run_demo.py --output experiments/payment-authorization-pilot/generated
```

デモは一時的な模擬鍵と非公開の設定・保存領域を作ります。公開出力は`summary.json`、
`admission-record.json`、元の`provider-receipt.json`の3つです。合成した要求、公開検証情報、
署名付き声明、判定、件数、模擬残高を含みます。秘密鍵、接続用認証情報、データベースは出力しません。
同梱の公開鍵は同じデモ制御者による提示であり、評価者は信頼する鍵を別途決める必要があります。
実行ごとに鍵と署名は変わります。

[CI](../../.github/workflows/payment-authorization-pilot.yml)は新しい試験、元の実行系試験、公開デモを実行し、
上記3ファイルだけを保存します。[オフライン証拠実験](../payment-api-evidence/README-ja.md)の形式と
試験は維持し、将来の送出や結果を作って事前の認可に使うことはしません。

## 検証範囲

試験は**固有の20件**です。適格で異なる承認者、要求・ポリシーの結合、不明・失効状態、実際のSQLiteロック、
承認記録と送出記録の一括ロールバック、コミット前後のSIGKILL、別プロセスの並行実行、同じインスタンスでの
入力分離、古い送出記録、履歴記録の整合性を検証します。同じ20件をPython最適化モードでも実行し、
再実行を別の試験件数には数えません。元の実行系は28件を維持します。

正常系の2クライアント競合試験では、各ワーカーの初期化完了を確認してから両方を進め、SQLiteの待ち時間を2秒に制限します。
成功した送出権の取得が1件、既存の使用済み記録の観測が1件、POST・振替が1件という条件は維持します。
意図的に短い待ち時間で保存ロック失敗を起こす試験と、実行系の既定値は変更しません。

ロック待ちの時刻試験では、実際の書込みロック中にクライアント時刻を過去から現在へ進め、時刻を取得する位置を確認します。
時刻源の認証を検証する試験ではありません。保存内容の破損試験では、制御者が意図的にSQLの更新ガードを外して外側の
ダイジェストも再計算し、元の署名・判定の矛盾が検出されることを確認します。管理者への隔離を示すものではありません。

## 入力と信頼範囲

| 入力 | 検証する対応 | 信頼の限界 |
|---|---|---|
| 別途採用したポリシー | 文脈、許可した口座・受取先、金額上限、有効期間 | ローカルの合成ポリシーであり、銀行の規則や顧客の同意ではない |
| 起票者と承認者の署名付き声明 | 検証した鍵、役割、正確な要求・ポリシーのダイジェスト、有効期間 | 鍵が2つあるだけでは不十分。採用済みの対応表で異なる人物であることが必要 |
| 採用した本人情報の対応表 | 検証した公開鍵の人物、役割、適用範囲、有効期間 | テスト用の人物識別子であり、実在の本人や組織上の独立性を確認していない |
| 署名付き状態情報 | 信頼する状態発行鍵、要求・承認との対応、状態、判定時点の鮮度 | 提示された時点情報であり、権威元への照会や現実の最新失効状態の保証ではない |
| ローカル判定時刻 | SQLiteの書込みトランザクションを取得した後の実時刻 | 外部認証された時刻源や時計の巻き戻し対策はない |

呼出し側が指定した鍵や人物名、`approved: true`のような真偽値で条件を置き換えることはできません。
要求、設定、元の署名付き証拠は正規化したスナップショットを使い、処理中の承認をアダプターの共有可変状態に
置きません。変更後の決済内容に別の署名が付いても、元の要求に対する承認を流用できません。
金額上限は1要求ごとであり、累計予算、不正検知、業務上の重複支払い検知ではありません。
ポリシー内の主体・認証情報の識別子は設定上のラベルです。呼出し側の本人確認や、エージェントによる別の鍵所持証明は
実装せず、信頼するローカル制御者からの呼出しを扱います。

## 保存と送出の順序

1. 専用の決済要求と、その呼出しに対応する証拠を取り込む。
2. 既存の記録領域で`BEGIN IMMEDIATE`を取得する。
3. 操作ID・冪等性キーが使用済みか先に確認する。同一要求なら新たな承認判定の保存やPOSTを行わない。
4. 新しい要求に限り、現在の実行世代を確認し、時刻を取得してポリシー・異なる承認者・署名付き状態を検証する。
5. 模擬条件を満たす場合だけ、元の証拠・判定記録と`CLAIMED`を同じトランザクションで保存する。
   コミット後に1回のPOST機会を得る。途中の中断や拒否で片方だけを残さない。
6. 元の実行時パイロットの結果証明検証、確定結果を後退させない保存、読み取り専用照合を使う。

承認記録の表は元の送出記録に対応付け、元の記録を保持します。SQLの制約・トリガーは通常の処理を支えるもので、
ホスト管理者に対する改ざん不可能な保存ではありません。元の承認・状態情報の署名は、採用した鍵の下で検証できます。
ローカルの承認判定記録自体には別のゲート署名はありません。同梱の公開鍵・本人情報だけで、その外部由来は確立できません。

## 決済結果と承認判定を分けて読む

`state`は決済結果、`mock_admission`は合成した事前条件の判定です。既存のオフライン検証器の4つの判定や、
VAPの規範的な判定値を置き換えません。

| 模擬承認の判定 | 新しい送出 | 意味 |
|---|---|---|
| `AUTHORIZED` | 使用済み記録を作り、1回のPOST機会を得られる | 記録した判定時刻に合成した条件が成立した |
| `DENIED` | 新しい使用済み記録・決済POSTを作らない | 同一人物の二重承認や失効状態など、検証済みの条件が矛盾する |
| `UNKNOWN` | 新しい使用済み記録・決済POSTを作らない | 欠落、検証不能、古い状態情報などで必要な根拠が成立しない |

新規の送出を止めた場合の結果は`REJECTED`です。保存前の拒否を永続保全する否認ログサービスはありません。
保存障害は認可や未実行の証明ではありません。承認条件が成立しても応答を失えば決済結果は`UNKNOWN`であり、
正しい要求に結び付いた提供者の署名付き結果によって確定します。

すべての結果で`business_authorization_verified: false`、`production_gate: false`、
`automatic_retry: false`、`synthetic: true`を維持します。`AUTHORIZED`は設定した模擬条件の成立であり、
独立した本人確認や本番業務の承認を実証した意味ではありません。

## 再提示・復旧・古い送出記録

同一要求は、承認の期限切れや後の失効情報があっても、最初に保存した承認記録と送出記録を使います。
これは過去の結果であり、新しい送出許可ではありません。照合は決済POSTを行わず、使用済み状態を解放・交換・再許可しません。
新しく提示した証拠で元の承認記録を上書きすることもありません。

読み出す際は、保存したポリシー、検証鍵・本人情報、状態情報の許容経過時間、元の判定時刻を使い、元の署名付き証拠と
対応付けを再検証して保存済みの判定を再現します。この履歴の整合性確認は、現在の時刻や権威元の状態による再認可ではなく、
保存した信頼設定の由来を独立して証明するものでもありません。

`recheck_record(record_bytes)`で、この限定された履歴再現をオフラインで行えます。`SUPPORTED`の場合も
`recorded_inputs_only: true`、`independent_trust_established: false`、`current_authorization_asserted: false`
を返し、同梱された署名が検証できたことと、独立した信頼・現在の認可を区別します。

元のアダプターで作った記録に承認記録がなければ、決済結果を保持した上で承認は不明とします。
後から承認を付けて過去の送出を正当化しません。提供者の結果証明が一致しても、このゲートの承認があった証明にはなりません。

## 今回の対象外

状態情報は許容した鮮度内でも最新とは限りません。ローカルの使用済み記録を確定した後、提供者側で作用するまでに
失効や期限切れが起こる可能性があります。連続的な失効保証、権威元の状態更新と銀行実行の不可分な取引、
最新状態の照会、既に取得した送出機会の取消しは実装していません。

提供者は元の接続用認証情報を検証し、今回の承認形式自体は検証しません。その認証情報を持つ主体は、元のアダプターや
提供者へ直接アクセスしてゲートを迂回できます。全役割・鍵は同じ運用者・ホスト利用者の管理下にあり、OS隔離、
特権経路の迂回防止、独立観測は実証しません。

独立収集者・外部アンカー、拒否ログの収集保証、企業の本人管理、実際の承認UI、銀行固有の決済完了、保存の巻き戻しや
完全な電源断への保証はありません。権威元が新しい操作ID・冪等性キーの組を承認すれば、業務上重複する支払いは作れます。

**PAY-02/PAY-03**の承認者・要求結合、**PAY-04**の提示された状態情報、既存の**PAY-06**復旧処理との接続の一部を
実行時に検証します。PAY-01〜PAY-08全体、VAP適合、新しいプロファイル、正式採択、独立再現、本番準備完了は主張しません。
[決済提案](../../proposals/payment-api-evidence/README-ja.md)も参照してください。
