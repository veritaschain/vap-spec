# 管理された模擬決済の実行時パイロット

**状態：未採択の参考実験。** [English](README.md)

`127.0.0.1`上の実際のHTTPサービスと、模擬残高を保存するSQLiteを動かします。
クライアントは要求の使用済み状態を保存してから、提供者へ1回のPOSTを行います。
同じ要求の再提示と、読み取り専用の照合では、保存した識別情報と元の署名付き結果を使います。
銀行、実資金、外部サービスには接続しません。

このパイロットは、**信頼する呼出し側が業務上の認可を済ませた後**を対象にします。
起票者・承認者の確認、認証情報の失効、実際の認可ポリシー、収集サービスの稼働状態は検証しません。
各結果に`business_authorization_verified: false`と`automatic_retry: false`を明示します。
模擬提供者へ接続するための認証情報は、本人の承認や業務上の認可証明ではありません。

別の[承認パイロット](../payment-authorization-pilot/README-ja.md)は、この基本処理の前に合成した起票者・承認者の
条件を検証し、新しい使用済み記録と承認記録を一括保存します。信頼範囲とレポートは別であり、
この基本アダプターを直接呼ぶ場合に業務上の認可を検証するわけではありません。

追加の[収集パイロット](../payment-collector-pilot/README-ja.md)では、この合成承認に別プロセスの証拠保全を接続し、
最初の管理されたPOST前に収集条件を確認します。証拠回収で使用済みの送出機会を復活させません。
独立運営の保管は実証せず、この基本処理の業務認可の範囲も変更しません。

[オフラインの決済証拠検証器](../payment-api-evidence/README-ja.md)は、別の事後検証ツールとして維持します。
本実験では将来の送出観測や結果証明を作って新しい要求を認可しません。
専用の実験用要求・結果形式を持ち、VAP Evidence Packや既存検証器のレポート形式への適合は主張しません。

## 実行方法と公開出力

Python 3.12、`cryptography`、SQLite、実際のループバック通信とプロセス操作が必要です。
SIGKILLの試験はPOSIX環境を対象とします。必要な機能がなければ試験失敗とし、スキップや模擬成功にはしません。

正常系の2クライアント競合試験では、両ワーカー自身の初期化完了を確認してから送出権の取得へ進め、SQLiteの待ち時間を
2秒に制限します。取得・POST・振替が各1件という条件を維持し、意図的に短い待ち時間でロック失敗を起こす試験と区別します。
遅延の保証や、実行系のタイムアウト既定値の変更ではありません。

```sh
python -m pip install -r experiments/payment-runtime-pilot/requirements.txt
python -W error::ResourceWarning -m unittest discover -s experiments/payment-runtime-pilot/tests -v
python experiments/payment-runtime-pilot/run_demo.py --output experiments/payment-runtime-pilot/generated
```

デモは一時的な提供者・クライアントの保存領域、署名鍵、接続用認証情報を作ります。
提供者が模擬振替をコミットした後、応答を返す前に接続を閉じます。クライアントの結果は`UNKNOWN`です。
同じ要求を再提示しても送出しません。GET照会で保存済みの結果証明を取得すると、ローカルの模擬振替について
`SETTLED`になります。その後の再提示は、提供者へ再接続せず同じ保存結果を返します。

公開出力は`summary.json`と、元の署名付き結果`provider-receipt.json`です。
合成要求、公開鍵、結果、結果証明のハッシュ、実際の要求件数、模擬残高を含みます。
秘密鍵、接続用認証情報、データベースは含めません。公開鍵はデモの制御者が示すものであり、独立した出所の
証明ではありません。毎回新しい鍵を作るため、署名は実行ごとに変わります。

[専用CI](../../.github/workflows/payment-runtime-pilot.yml)ではプロセス試験とデモを実行し、この2つの公開ファイルを保存します。

## 実際に測るもの

| 観測値 | 意味 |
|---|---|
| 提供者のPOST件数 | 模擬サービスが受け取った書き込み要求。実際の振替回数と別に数える |
| 提供者の照会件数 | 決済状態の照会。残高変更や使用済み要求の解除は行わない |
| 決済記録と振替件数 | 保存された模擬結果と、成功したローカル振替。失敗結果には証明があっても振替はない |
| 模擬残高 | 提供者のSQLiteに保存された送金元・受取先の値 |
| クライアントの記録状態 | 使用済みの送出識別情報と、その後に保存した真正な結果 |

照合では観測件数を更新し、クライアントが取得結果を保存することがあります。
「読み取り専用」は、決済の再書き込み、残高の変更、使用済み状態の解除を行わないという意味です。

## 要求の同一性と永続状態

使用済み要求を区別する範囲は、テナント、環境、対象API、冪等性ドメインの組です。
その範囲内で、**操作IDと冪等性キーの両方を一意にし、正確な要求内容と対応付けて保持**します。
要求には設定ハッシュ、復旧世代、送金元、受取先、整数の金額、通貨と単位も含みます。
金額は正規化した10進文字列と範囲を制限した整数演算で扱い、浮動小数点や暗黙の通貨換算は使いません。

| 再提示された内容 | 動作 |
|---|---|
| 操作ID・キー・内容が同じ | 保存結果または不明状態を返す。新しいPOSTは行わない |
| 同じ操作IDでキーだけ変更 | 矛盾として拒否し、元の記録を保持 |
| 同じキーで操作IDだけ変更 | 矛盾として拒否し、元の記録を保持 |
| 同じ識別情報で金額・受取先などを変更 | 矛盾として拒否 |
| 同じ識別情報で設定・復旧世代を変更 | 新しい使用管理の範囲を作らず、既存の要求を解放しない |
| 両方のIDを変更 | 別の要求。本実験だけでは業務上同じ支払いだと識別できない |

クライアントと提供者は別のデータベースを使います。`BEGIN IMMEDIATE`と一意制約により、並行要求のうち
1つだけが送出権を取得し、その記録をコミットしてから通信します。提供者では要求、安定した署名付き結果、
成功時の引き落としと入金を1つのトランザクションで保存します。提供者へ直接同じ要求を再送しても結果は同じで、
振替は増えません。ただし、そのPOST自体は件数に残るため、「振替1回」と「要求1回」を混同しません。

SQLiteはWALと`synchronous=FULL`を使います。これはプロセス強制終了試験のローカル保存の前提であり、
記憶装置の虚偽応答、電源断、データベース削除、バックアップ巻き戻し、古いスナップショットの復元に対する
保証ではありません。SQLiteの一次資料は[トランザクション](https://www.sqlite.org/lang_transaction.html)と
[同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)を参照してください。

保存領域には対象範囲と提供者・検証鍵の対応も保持し、不整合な条件での再利用を拒否します。
提供者は同じデータベースと検証上の本人性を維持し、別の一時ポートで再起動できます。
復旧世代や接続用認証情報を使用管理の名前空間に含めないため、更新によって既存の要求IDは未使用に戻りません。
過去の照合は元の要求を使います。鍵のライフサイクルや失効の強制は実装していません。

世代の確認は、それぞれのデータベースのトランザクション内で、新しい送出権や提供者側の振替に適用します。
世代を変えても、既に送出権を取得した処理をクライアントと提供者にまたがって不可分に取り消すことはできません。
分散した確認と実行の一体化や、継続的な失効の保証は行いません。

## 状態と障害時の扱い

| 結果 | 意味 |
|---|---|
| `SETTLED` | ローカル模擬振替に対応する真正な結果を保存済み。再提示にはその結果を返す |
| `FAILED` | 対応する模擬失敗結果を保存済み。決済成功とは区別する |
| `UNKNOWN` | 使用済み要求の結果が不明。明示的な読み取り専用照合を使い、自動再送しない |
| `CONFLICT` | 使用済み識別情報と内容・別名の対応が矛盾。元の記録を保持する |
| `REJECTED` | 入力や対象範囲が不適合。遠隔側の過去の決済履歴を判定したものではない |
| `JOURNAL_UNAVAILABLE` | 必要な保存を確認できない。何も保存されなかったとは推定しない |

送出意図の保存は、通信が実際に行われた証明ではありません。保存後・POST前にワーカーを強制終了すると、
試験の制御者が提供者の要求件数ゼロを確認できても、クライアントは未解決状態を保持します。
提供者の照会で記録が見つからなくても、その要求の再送を許可しません。
この設計は、自動的な処理完了より、結果が曖昧な要求の使用済み状態を保持することを優先します。

提供者がコミットして応答だけが失われた場合や、受領後・結果保存前にクライアントが終了した場合も、
再起動後に元の使用済み記録を保ちます。復旧では提供者を照会して元の署名付き結果を確認し、
新しい要求や提供者の代わりの署名を作りません。

## 試験範囲とPAY-06／PAY-08との対応

実際のループバック通信、別々の保存領域、並行プロセス、ワーカー・提供者のSIGKILLと再起動、
SQLiteの実際の書き込みロック、コミット境界の障害注入を使います。判定値だけで合否を決めず、
要求数、振替件数、元の結果証明、残高を確認します。障害フックは試験制御者が設定し、決済要求からは指定できません。

これにより、**PAY-06**の永続的な使用管理、応答喪失、読み取り専用の復旧を、専用の模擬形式で検証できます。
**PAY-08**については、ローカル記録を保存できることを送出の前提にする部分と、設定・世代更新後も使用済み状態を
保持する部分を対象にします。独立した収集者の停止、収集チェックポイントの復旧、認証情報の失効、
侵入者の根絶、8つすべてのアダプター受入条件の実証には拡張しません。

業務上の認可と、実際に観測した制御経路は別の問題です。既存のオフライン実験とその結果は維持します。
[事前記録ゲート](../pre-record-gate/README.md)の保存・再送抑止パターンを参考にし、本実験では金額、模擬残高の
変化、範囲付きの操作ID・冪等性キーを扱います。既存の`create_record`処理結果を決済結果と読み替えません。

## 保証範囲

通信先は明示的なループバックに限定し、経路と要求サイズを固定・制限します。プロキシの継承やリダイレクト追従は
行いません。提供者は制御者が用意した一時鍵で結果を署名し、クライアントは固定した公開鍵と正確な要求・提供者の
対応を検証してから確定結果を保存します。秘密鍵と接続用認証情報の設定ファイルは、所有者だけが読める状態にします。

すべてのプロセスと鍵は同じ運用者・ホスト利用者が管理します。これはアプリケーション上の役割分離であり、
OSによる隔離、独立した観測、悪意ある管理者への耐性、本番の証拠保管構成を示しません。
本実験の状態は期限なしで保持し、削除、巻き戻し、複数リージョンの復旧は扱いません。
両方の要求IDを変えれば業務上重複する支払いを作れるため、未解決の要求を解消する目的で新しいIDを自動生成してはいけません。

汎用的なexactly-once、実銀行との互換性、本番可用性、独立再現、VAP適合、新しいプロファイルや規範要件は主張しません。
今後の運用統合には、明示的に許可された決済連携、上流の業務認可、本人・鍵の管理、独立収集、プライバシー・保存期限、
管理されたストレージ復旧の検討が必要です。
