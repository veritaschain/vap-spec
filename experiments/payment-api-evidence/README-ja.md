# 決済APIの証拠検証実験

**状態：未採択の参考実験。** [English](README.md)

[決済APIの提案](../../proposals/payment-api-evidence/README-ja.md)で示した証拠上の区別を、
合成データで実行できるようにしたオフライン検証器です。決済エンドポイントや実資金を使いません。
CRAFTY FALCONの再現、銀行アダプター、VAP適合の実装ではありません。

署名と、その署名が結び付ける内容を検証します。送金先の変更、認証情報の失効、迂回経路の観測に
正しい署名が付いていても、それを「認可された送金」と判定しないことを確かめます。

## 4つの問いを分ける

| 判定項目 | 呼出し側が採用した信頼の前提の下で、`VALID`が意味すること |
|---|---|
| `integrity`：記録の検証 | 提示された証拠を、別途設定した役割ごとの鍵で検証できる。収集の網羅性や表明内容の真実性は保証しない。 |
| `authorization`：認可 | 観測された送出が、個別操作・ポリシー・起票者と承認者の本人／役割・承認期限・最終状態の観測に対応する。送出時点の証拠を事後評価する。 |
| `execution_match`：実行との一致 | 真正性を確かめた送出と提供者の証拠が、合成要求の正確な内容と確定的な結果に対応する。結果は別途示し、`failed`や`reversed`でも記録の対応が正しければ成立し得る。決済成功とは同義ではない。 |
| `control_state`：観測した制御状態 | 経路と収集者の署名付き観測が、設定・復旧世代・提示記録の収集範囲を、指定経路と観測時点に限って裏付ける。 |

`INVALID`は、構造や署名の検証失敗、または当該項目に関する真正な証拠の矛盾です。
`INDETERMINATE`は、必要な証拠、信頼した出所、本人対応、鮮度、観測範囲などが不足する状態です。
別の証拠が不足していても、確認済みの矛盾を消しません。真正性を検証できない表明から、その出来事が
実際に起きたとは判定しません。

これらは実験の判定値であり、VAPの規範的判定値ではありません。全体の安全判定、送金許可命令、
「VAP合格」は返さず、`read_only: true`と`automatic_retry: false`を示します。

## 実行方法

対象を限定した[GitHub Actions](../../.github/workflows/payment-api-evidence.yml)はPython 3.12を使います。
試験は`unittest`と`cryptography`で動き、試験実行中にネットワークへ接続しません。

```sh
python -m pip install -r experiments/payment-api-evidence/requirements.txt
python -m unittest discover -s experiments/payment-api-evidence/tests -v
```

このディレクトリで、正常な合成証拠のレポートを取得できます。

```python
from fixtures import make_fixture
from payment_evidence import canonical_json, verify_bundle

bundle, trusted_keys, identities, at = make_fixture("authorized")
report = verify_bundle(
    bundle, trusted_keys, identities=identities, evaluation_time=at
)
print(canonical_json(report).decode("utf-8"))
```

`python fixtures.py`で24ケースの合成結果一覧を出力できます。コマンドライン検証器は、
`--bundle`、`--trust`、`--identities`、`--at`を別々の入力として受け付けます。
信頼鍵のJSONでは公開鍵の生バイト列を小文字の16進数で表します。レポートを標準出力へ返し、
4つの証拠判定がすべて`VALID`なら終了コード`0`、それ以外は`2`です。
これは決済成功を意味しません。対応する`failed`や`reversed`でも、4つの証拠判定が成立する場合があります。

APIは入力の写しを検証し、時計の読み取り、外部接続、要求の送出、送金の再試行、台帳更新を行いません。
同じ証拠を再検証しても操作IDは消費されません。応答がなければ結果は不明のままであり、読み取り専用の
照合には提供者側の証拠を別途取得する必要があります。

## 信頼、本人対応、要求の正確な内容

信頼鍵、本人・役割の対応表、評価の基準時刻は、証拠一式の外から呼出し側が渡します。
本人対応は検証済み公開鍵を索引にするため、鍵IDの名前を変えても別人にはなりません。
役割、テナント、環境、有効期間を確認し、2つの鍵が同一人物に対応すれば職務分離に反する証拠として扱います。
対応表がなければ、本人性の確認は不明です。

設定した役割別の鍵は、呼出し側が選んだ今回の評価範囲について信頼する前提です。
各提供者の鍵を特定の`provider_id`だけに限定したり、各ポリシー鍵を特定のテナントだけに限定したりする
対応表は実装していません。役割について信頼された鍵は、その役割の表明を行えます。
無関係な提供者やテナントの鍵を、共通の権限集合として混在させるべきではありません。
発行主体別の鍵の権限、鍵のライフサイクルと失効は別途検討が必要です。

試験用署名鍵の生成元は公開された合成データです。証拠の生成も単一プロセスで行います。
鍵や人物IDを分けただけでは、実在する本人、独立した組織、誠実な観測者、信頼できる時刻源を立証しません。
運用時には、これらの条件を別途確立する必要があります。

この実験は専用のスキーマと署名ドメインを持ちます。署名は鍵IDと完全なペイロードを対象とし、
記録間の参照は署名付きエンベロープ全体を特定します。JSONの対象範囲を制限し、重複キー、浮動小数点、
NFCではない文字列、曖昧な整数表現を拒否します。RFC 8785の実装は主張しません。

| 証拠のスロット | 呼出し側が鍵を設定する役割 | 主な結合内容 |
|---|---|---|
| `policy` | `policy_authority` | 許可範囲、金額と単位、設定、世代、提供者、有効期間 |
| `maker_approval`、`checker_approval` | `approver` | 個別操作とポリシー。別途渡した本人・役割の対応も確認 |
| `final_status` | `status_authority` | 認証情報の状態、個別承認、操作、設定、世代 |
| `dispatch` | `execution_observer` | 実際の操作と要求バイト列、ポリシー、承認、最終状態、制御記録、時刻 |
| `provider_receipt` | `payment_provider` | 操作、要求、送出、提供者と対象API、結果 |
| `control` | `control_observer` | 指定経路、操作、設定、世代、観測時刻 |
| `collector` | `collector` | 保全した個別署名記録、既知の欠落、チェックポイント、世代 |

各署名ペイロードは証拠の種類と実行IDも結び付けます。正確なフィールドと型の制約は、
[`payment_evidence.py`](payment_evidence.py)の`*_SCHEMA`に定義しています。
試験データの参照更新ヘルパーは、新しい合成表明を発行するためのものです。実際の事件証拠の書き換えには使いません。

版を固定した合成要求形式で、操作ID、テナント、環境、宛先API、送金元、受取人、正確な金額と通貨単位、
認証情報、設定、ポリシー、冪等性の適用範囲、復旧世代を結び付けます。実際の要求バイト列を、承認された
操作と観測された操作の両方に照合します。この解釈は合成形式に限定され、任意の銀行データの解読や、
実在する受取人の本人確認、送金先の妥当性の保証には拡張しません。

認可の評価対象は、**真正性を確認した時刻に観測された送出**です。呼出し側の評価基準時刻より後の証拠を、
既に取得できていたものとして扱いません。後の時刻を持つ署名付き観測は`excluded_after_horizon`に示し、
内容の判定から除外しますが、提示された署名自体は検証します。時刻は情報源の申告値であり、実際の受領時刻を
証明するものではありません。最終状態と承認の順序・鮮度を送出時点で、本人の資格を承認発行時点でも確かめますが、
新しい状態観測だけで、状態確認から実行までの時間差を解消することはできません。

別項目の`settlement_confirmed`は、対応する合成提供者の表明が、このレポート内で決済完了を裏付けるという
意味です。銀行送金の独立した確認ではありません。対応を確認できず`status`が`unknown`のときも、
`reported_status`に出所を付けた提供者の表明を残すことがあります。

## 8つの候補群に対する検証範囲

変更しない正常対照と、新たに署名した矛盾する観測を含め、以下の証拠上の区別を検証します。
提案中の、状態を持つアダプターの受入試験全体を実行するものではありません。

| 候補群 | この実験で確かめること | 未実証の範囲 |
|---|---|---|
| PAY-01 | 承認・送出・提供者・限定された制御観測が対応すると、4項目を個別に裏付けられる。 | 実際の決済完了、送金先の安全性、本番運用の準備完了。 |
| PAY-02 | 同一人物の二重承認は矛盾、本人対応の不足は不明。 | 本人確認基盤との連携、組織的な独立性。 |
| PAY-03 | 送金先・金額・通貨・テナント・環境の変更は、署名が正しくても承認と実行の結合に反する。 | 合成要求形式以外の銀行固有データの解釈。 |
| PAY-04 | 送出前の明示的な失効と、状態の観測不足・古さを区別する。 | 確認と実行の不可分な強制、継続的な失効監視。 |
| PAY-05 | 観測した迂回は制御前提に反し、必須経路の未観測は不明になる。 | 実際のネットワーク／クラウド隔離、全経路の発見。 |
| PAY-06 | 応答喪失は繰り返し評価しても不明のまま。要求内容の結合の矛盾を検出する。 | 永続的な使用済み台帳、並行要求の重複抑止、障害復旧、実際の送金の再実行。 |
| PAY-07 | HTTP 200を決済完了とみなさず、別操作の真正な結果証明を不一致として扱う。受理・処理中・確定結果を区別する。 | 実銀行との照合、独立した資金移動の観測。 |
| PAY-08 | 宣言した収集欠落を保持し、確認できた旧世代や保全記録の参照違いを矛盾として扱う。 | 実際の収集停止、鍵更新、復旧処理、侵入者の根絶。 |

収集者の表明は、保全した証拠と既知の欠落を記述します。未収集の記録を回復せず、あらゆる欠落の不在を
証明せず、独立した外部アンカーにもなりません。本実験はVAPのMerkle anchoring、アンカーの連続性、
Completeness Invariantを実装していません。Ed25519とハッシュを使うだけでVAP適合にはなりません。

## 既存実験との関係と次の段階

[ウォレット証拠実験](../wallet-authorization-evidence/README.md)のJSON制限・署名検証の小さな処理パターンを
参考にし、決済専用の形式と署名ドメインで実装しています。既存の実験と固定済み証拠アーカイブは維持します。
[事前記録ゲート](../pre-record-gate/README.md)、[制御状態の実験](../control-state-evidence/README.md)、
[収集者パイロット](../incident-collector-pilot/README.md)は別の限定された実行実験であり、その結果を
決済の試験結果に置き換えません。

別途追加した[管理された実行時パイロット](../payment-runtime-pilot/README-ja.md)では、ループバックの模擬API、
永続的な使用管理、再起動、並行要求、応答喪失、読み取り専用の照合を検証します。専用の形式を使い、
呼出し側が業務上の認可を済ませた後を対象にします。この事後検証器を実行時の認可ゲートに変更せず、
将来の観測を作って入力することもありません。このディレクトリの検証器は状態を持たず、既存ケースも
引き続き合成証拠の意味を検証するものです。本番には銀行固有の意味、信頼した本人・結果証明との
連携、保護されたポリシー状態、プライバシーと保存期限、独立収集、特権による迂回の検討も必要です。
学校AIの通知・評価環境に関する提案は、別の設計作業として扱います。

実在する口座識別子、顧客データ、秘密情報、提供者の認証情報、資金は使用しません。
本実験は新しいプロファイル、規範要件、規制当局の承認、認証、独立した第三者検証を成立させません。
