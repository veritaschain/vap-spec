# 収集先の停止・復旧を測る実験

この実験は、UP-08 で残っていた「監査記録の収集先が停止したとき、管理下の
送信経路がどう振る舞うか」を実際の別プロセスと HTTP 通信で測ります。
仕様適合や組織全体の漏えい防止を認定するものではありません。
VAP の規範仕様は v1.2 Draft 3 のままです。

## 実際に行うこと

収集先には、要求 ID、送信先・テナント・ポリシーを含む対象のハッシュ、
ペイロードのハッシュとバイト数、署名された許可のハッシュを送ります。
ペイロード本体を収集先のログに保存しません。本体は別の受信プロセスが
受け取り、実際に受信したバイトのハッシュと長さを記録します。

ゲートは収集先の保存受領証を検証した後、新しい乱数に結び付く照会を行い、
直前の状態を確認します。現在有効なポリシー、許可、鍵と照合し、最終評価が
`ALLOW` の場合だけ本体送信を一度試みます。

保存後に応答だけ失われた場合、「保存されていない」とは判断しません。
最初の送信を止め、同じデータベース・鍵・識別子・エンドポイントで収集先を
再起動して、保存状況を照会します。この照会は本体送信を再開しません。
送信には、新しい要求 ID に対して明示的に許可された別の要求が必要です。

| 表示 | 読み方 |
|---|---|
| `ACKNOWLEDGEMENT_NOT_ESTABLISHED` | 保存を確認できる応答を得ていない。未保存の証明ではない |
| `FRESH_READBACK_CONFIRMED` | 今回の新しい照会に対して、元の記録と受領証を検証した |
| `BLOCKED_WITHOUT_ATTEMPT` | 本体の送信は試みていない。メタデータ通信は発生し得る |
| `REPLAY_NO_SEND` | すでに永続化した同じ要求なので、再送しない |
| `RECEIPT_CONFIRMED` | 指定した受信者の署名で、測定した本体との一致を確認した |
| `OUTCOME_UNKNOWN` | 応答や結果保存が不確実。再送してよいという意味ではない |

## `ALLOW` と事後の `REVIEW` が両方残る理由

収集先を確認した時刻と、本体を実際に送った時刻は異なります。既存の評価器は
両方を区別するため、最終ゲートで `ALLOW` でも、送信時刻そのものの収集先の
証拠がなければ事後の `observed_action_authorization` は `REVIEW` です。
評価を良く見せるために確認時刻や送信時刻を書き換えません。

この実験で示すのは、送信前の一点で必要条件を確認したことです。収集先が
その後も継続稼働したことや、確認と送信が不可分であることは示しません。
収集先の受領証も、AI 事業者による処理・学習利用・完全削除の証明ではありません。

## 実行と保存済み結果の再検証

リポジトリ全体を取得し、このディレクトリで README のコマンドを実行します。
18 件すべてで実際のプロセスとループバック HTTP を使用します。ソケットを
利用できない実行環境では失敗として扱い、スキップして成功扱いにしません。
Python 3.12 と 3.14 の CI でも同じ確認を行います。

公開用ファイルは `generated/public/`、実験中のデータベースは `generated/runtime/`
に分けます。公開ファイルには秘密鍵や本体の平文を含めません。

再検証では、信頼できる経路で入手した `summary.json` の SHA-256 を指定します。
同じ未検証の配布物にあるハッシュだけを信頼しても、配布元は確認できません。
再検証が確認するのは、ファイルの同一性、署名、対応関係、時刻の整合性、
既存評価器の再計算、固定された期待値です。通信を再実行せず、第三者による
独立観測や独立再現を意味しません。

元の 154 個の実行入力、53 件の保存済みケース、23 件の提案カタログと歴史的な
対応表は変更しません。これらとの同一性は起動前と実行後にハッシュで確認します。
